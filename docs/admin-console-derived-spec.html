관리자 페이지 구성안 — 현재 사용자 화면 구현 기반 도출

TALKPIK v13 · derived planning reference (설계 입력용 참고 문서)
작성: 2026-06-04 · 근거: docs/user-admin-data-consistency.md, docs/admin-scope-boundary.md, docs/user-admin-consistency-method.md

⚠️ 먼저 읽어야 할 범위 경고 (중요)

이 문서는 "관리자 페이지를 새로 만들라"는 지시서가 아닙니다.

  1. 관리자(admin) 앱은 이 저장소가 아니라 별도 저장소 topik-ai가 소유합니다(Vite+React+AntD, 별도 git). 이 저장소(v13)는 사용자 화면 전용입니다.
  2. 그래서 이 문서는 "지금 v13에 실제로 구현된 사용자 기능을 운영하려면 관리자 콘솔에 어떤 화면·기능이 필요한가"를 거꾸로 도출한 설계 입력 자료입니다. 나중에 있을 admin↔v13 정합(sync) 단계의 참고용입니다.
  3. 이 문서를 근거로 v13 안에 admin 코드를 새로 만들거나 확장하면 안 됩니다. 데이터 스키마가 admin 우선으로 설계됐기 때문에, 사용자 화면을 스키마에 맞추는 방향입니다.
  4. 화면 명세의 최종 권위는 topik-ai/docs/specs/admin-data-contract.md와 topik-ai/docs/page-sync/*.md에 있습니다.
한 문장: "지금 v13이 굴러가게 하려면 관리자가 무엇을 보고 무엇을 만질 수 있어야 하는가"의 지도 — 만드는 작업이 아니라 만들 때를 위한 밑그림.

1. 한 줄 요약

지금 v13에 구현된 사용자 기능(회원·문제·쓰기 제출·AI 피드백·추천·결제·알림·라이브러리)을 운영하려면, 관리자 콘솔은 크게 9개 영역이 필요합니다. 이 중 직접 만지는(CRUD) 영역은 "문제은행"과 "회원/결제 카탈로그"뿐이고, 나머지 대부분은 사용자 소유 데이터라서 "읽기/지원/분석" 전용으로만 두는 것이 안전합니다.

2. 도출의 출발점 — 지금 "실제로 구현된 것"

2-2. 이미 이 저장소에 "동결된 채" 존재하는 admin 코드 (확장 금지 / 참고만)

v13 안에는 과거 만들어졌다가 동결(frozen)된 최소 관리자 골격이 있습니다. 권위 있는 admin 구현이 아니며 삭제도 확장도 하지 않습니다.

주의: admin/org가 쓰는 조직(organizations/assignments) 스키마는 철회된 "전체 빌드" 지시 아래 추가됐던 항목입니다(dev에만 적용, 사용자 기능 미사용). 현재 사용자 화면 범위 밖이며 유지/롤백은 정합 단계 소유자 결정.

4. 화면별 상세 구성안

4-1. 문제은행(쓰기 문제) 관리 CRUD · 최우선

목적
TOPIK 쓰기 문제(51·52·53·54형)를 등록·검토·발행하고 사용자 노출을 통제.
화면
문제 목록(유형/상태/공개 필터), 상세(지문·자료·채점기준 rubric·모범답안), 첨부 에셋, 발행/검토 KPI.
동작
문제 생성·수정, 발행 토글(publish_status), 검토 상태(review_status), 공개범위(visibility), 에셋 업로드/교체.
데이터
problems, problem_assets + problem-assets 스토리지
권한
content_admin / platform_admin
topik-ai
Assessment > TOPIK 쓰기 문제은행(assessment_questions + 97문항 JSON). 필드/테이블 이름 다름 → 매핑 계약이 정합 1순위.
주의: topik-ai fixture는 문서(JSON) 중심이라 에셋 관리가 명시적이지 않음 → 에셋 관리 대상 여부 결정 필요.

4-2. 회원·계정 관리 상태변경 읽기·지원

목적
회원 조회 + 운영상 꼭 필요한 상태(차단/역할)만 통제. 프로필 본문은 사용자 소유.
화면
회원 목록(상태/플랜/역할 필터), 상세(프로필·학습목표·결제상태·최근활동), 가입/접속 KPI.
동작
상태 변경(profiles.status), 역할 부여(app_role), 지원 조회. 프로필 본문·학습목표는 기본 읽기.
데이터
profiles, learning_goals, avatars 스토리지
권한
상태/역할은 platform_admin, 조회는 지원 권한
topik-ai
Users > 회원 목록/상세. 매핑 이슈: v13 profiles ↔ topik-ai users, 이메일 출처(auth.users vs mock), 필드 매핑.
주의: learning_goals는 admin 화면 없음 — 관리할지 조회만 할지 제품 결정 필요.

4-3. 결제·구독 관리 카탈로그 CRUD 읽기·지원

목적
요금제 카탈로그 관리 + 사용자 구독/결제 조회·지원.
화면
요금제 목록, 사용자별 구독 상태, 결제 내역/영수증, 환불 상태.
동작
요금제 CRUD(subscription_plans), 구독/결제 조회, 환불 처리(정책).
데이터
subscription_plans, subscriptions(서비스가 씀), payment_history(서비스가 씀)
권한
platform_admin / 결제 운영 권한
topik-ai
Commerce > 결제 내역(commerce_payments), 환불(commerce_refunds), 이커머스(commerce_products/packages). 부분 겹침 — 1:1 아님. v13엔 별도 환불 테이블 없음.
주의: "구독 상태"와 "결제 거래"를 admin 모델에서 분리할 것.

4-4. 알림·메시지 읽기·지원

목적
발송 결과 추적 + (별도) 운영 캠페인 발송. 개인 알림 설정은 사용자 소유.
화면
발송 이력(채널/상태/수신자), 메일·푸시 템플릿, 대상 그룹.
동작
캠페인 템플릿/대상 관리(운영), 발송 이력 조회. 사용자별 설정은 조회만.
데이터
notification_settings(사용자 소유), notification_log
권한
메시지 운영 권한
topik-ai
Message > 메일/푸시(message_templates), 대상 그룹(message_groups), 발송 이력(message_histories). 사용자 설정 vs 캠페인 타겟팅은 다른 개념 — 합치지 말 것.

4-5. 쓰기 제출물·AI 피드백 읽기·지원 전용

목적
제출 글·AI 피드백을 품질 점검·고객지원 목적으로 조회. 편집 아님.
화면
제출물 본문(읽기), AI 피드백(전체/항목별/문장별), 피드백 생성 상태.
동작
조회·진단만. 필요 시 재생성 요청/오류 표시 정도.
데이터
writing_submissions(불변), writing_feedback, feedback_dimension_scores, sentence_feedback, writing_drafts
권한
지원/품질 권한(개인정보 최소 접근)
topik-ai
Users 상세 지원 탭 또는 Analytics에 read 형태. 직접 CRUD 화면 없음.
주의: 제출물 불변 유지. 열람은 개인정보 경계 + 읽기 전용 경로를 먼저 정의.

4-6. 학습 활동·추천 분석

목적
학습 활동·추천 결과 집계·분석. 추천 규칙은 선택적 운영.
화면
추천 실행 이력·요약, 추천 문항·이유·약점 태그, 풀이 시도 통계, 활동 추이.
동작
조회·분석. (선택) 추천 규칙/설정. 진행상황 직접 수정 금지.
데이터
problem_attempts, recommendation_runs, recommendation_items, study_events
topik-ai
Analytics / Content 후보. 직접 CRUD 없음.
주의: "추천 결과 CRUD"는 일반 admin 작업 아님 — 규칙 운영인지 생성물 관찰인지 명확히.

4-7. 라이브러리·리포트·내보내기 읽기·지원 전용

목적
저장 항목·비교 리포트·내보내기 파일을 지원 목적 조회.
데이터

topik-ai
대응 화면 없음. CS 요구 명확할 때만 읽기 경로 추가.

목적

4-9. 시스템·권한·감사 로그 (내부 운영)

목적

데이터

topik-ai

주의: B2C 노출 없음. v13 admin_audit_logs ↔ topik-ai audit_logs 매핑 필요.

5. 권한·역할 모델 (현재 v13 구현 기준)

역할범위접근 가능 영역(도출)
platform_admin전체모든 영역
content_admin콘텐츠문제은행, (읽기) 피드백 품질
org_admin조직조직 대시보드(동결, 범위 밖)

topik-ai에는 별도 RBAC(System > 권한 관리: system_roles/system_permissions/admin_accounts)가 있습니다. 최종 권한 모델은 정합 단계에서 매핑하며 B2C 사용자에 노출되지 않습니다.

6. "쓰기 가능" vs "읽기·지원 전용" 원칙 (가장 중요한 안전선)

가장 위험한 실수는 사용자 소유 데이터를 admin이 직접 편집(CRUD)하게 만드는 것입니다.

분류대상이유
✅ 직접 관리(CRUD) 적정problems/problem_assets, subscription_plans운영자가 만들고 관리하는 공급 측 데이터
🟡 상태/역할만 변경profiles(status/app_role)운영상 필요하나 본문은 사용자 소유
🔒 읽기·지원 전용제출물(불변)·피드백·초안·라이브러리·리포트·내보내기·구독·결제·알림설정사용자 소유·서비스 생성·불변 데이터. 직접 편집은 신뢰·무결성 훼손
📊 분석/집계 전용study_events, problem_attempts, recommendation_*, KPI원본 변경 금지, 집계 뷰로만
  1. 사용자 소유 데이터는 기본 읽기. CS 필요가 명확할 때만 읽기 경로 추가, 개인정보 경계 먼저 정의.
  2. 제출물(writing_submissions)은 불변 — admin도 수정 불가.
  3. 서비스가 쓰는 데이터(구독/결제/피드백/추천)는 admin이 직접 쓰지 않음.
  4. admin용 스키마를 새로 추가해 사용자 화면을 끼워 맞추지 않음 — 스키마 정합 이슈는 소유자 에스컬레이션.

9. 반드시 지킬 원칙 / 주의사항

  1. 이 문서로 v13에 admin을 만들지 않는다. admin은 topik-ai 소유, 정합은 사용자 화면 완료 후 단계.
  2. 스키마는 admin-first. 사용자 화면을 스키마에 맞춘다. admin용 스키마 신규 추가 금지(소유자 승인 시 예외).
  3. 사용자 소유 데이터는 기본 읽기·지원. 제출물 불변, 서비스 작성 데이터 직접 편집 금지.
  4. 상태/enum 용어 일치가 최대 리스크 표면(publish_status, profile status, 피드백 상태 등).
  5. 개인정보 경계 우선. 제출물·초안·피드백 열람은 최소 권한·읽기 경로·접근 로그를 먼저 정의.
  6. 이 문서는 실증(live DB CRUD) 전 단계. 실제 정합은 슬라이스별 검증으로 확정.
