# TALKPIK AI PRD

이 문서는 TALKPIK AI의 유일한 제품 SOT다. 사용자가 무엇을 할 수 있어야 하는지와 현재 범위를 정한다. 정확한 route는 `src/lib/routes.ts`, 현재 동작은 source와 tests, 데이터 구조·RLS·RPC는 migration SQL이 소유한다.

## 1. 제품과 사용자

TALKPIK AI는 TOPIK 학습자가 목표를 설정하고, 추천 문제와 쓰기 51~54번을 연습하며, 피드백과 복습으로 실력을 높이는 사용자 앱이다.

주요 사용자는 TOPIK I·II를 준비하는 한국어 학습자이며, 특히 혼자 쓰기 답안을 연습하고 구조화된 피드백을 받고 싶은 학습자를 우선한다.

제품이 보장할 핵심 가치는 다음과 같다.

- 현재 목표와 학습 상태, 다음 행동을 한눈에 이해한다.
- 자신에게 맞는 연습 문제를 찾아 바로 학습을 시작한다.
- 쓰기 51·52·53·54번 답안을 안전하게 작성하고 제출한다.
- 제출 결과와 피드백을 다시 보고 재도전한다.
- 저장한 문제와 학습 기록을 내 서재에서 복습한다.

## 2. 범위

### 현재 제품 범위

- 이메일·Google 기반 가입, 로그인, 인증 callback/error, 비밀번호 재설정과 가입 완료 절차
- 프로필, 언어, 학습 목표와 시험일 관리
- 홈·성장 현황, 문제 유형 추천, 문제 목록과 약점·다음 문제 추천
- TOPIK 쓰기 51~54번 작성, 초안 자동저장, 제출과 분석 상태
- 단답·장문 피드백, 이전 답안 비교, 다시 풀기
- 내 서재의 제출·피드백·초안·저장 문제 복습
- PDF 생성·다운로드와 서버 기준 quota
- 사용자 알림, 동의와 계정 탈퇴

### Future

- 독립 단어장과 고급 복습 묶음
- 실전 모의고사, OMR, 결과·성적 추이
- 게시판, 공지·이벤트 상세
- 고급 배지와 과거 피드백을 다른 언어로 다시 번역하는 기능

Future 항목은 제품 방향이지 현재 제공 약속이 아니다. 사용자가 별도로 범위를 열고 PRD·source·tests가 함께 갱신되기 전에는 구현 완료로 표현하지 않는다.

### Deferred

- 실제 LLM 기반 문제 생성, 채점·첨삭과 작성 중 AI 대화
- AI 사용량 한도와 실제 비동기 분석 provider
- 결제·구독 provider 및 실제 결제 처리
- 외부 이메일·메신저 알림 전송
- 법무 검토가 끝난 정식 약관·개인정보 문안

현재 mock, placeholder 또는 상태 UI가 있어도 deferred 기능을 실제 동작으로 오해하게 표시하지 않는다. 필요한 경우 `준비 중`과 사용자가 지금 할 수 있는 다음 행동을 함께 안내한다.

### 금지 범위

- 이 사용자 앱에서 admin 화면이나 운영 제어 기능을 새로 만들거나 확장하지 않는다.
- secret·token·service-role key를 사용자 화면이나 browser bundle에 노출하지 않는다.
- 승인 없이 원격 DB, 실제 결제·외부 발송·운영 데이터를 변경하지 않는다.

## 3. 핵심 사용자 흐름

### 가입과 첫 진입

1. 사용자는 가입 또는 로그인을 선택한다.
2. 신규 사용자는 이메일 확인, 필수 동의, 프로필과 학습 목표를 완료한다.
3. 완료된 사용자는 홈에서 학습 상태와 다음 행동을 확인한다.
4. callback 실패, 만료, 재전송 제한은 안전한 인증 오류 안내와 재시도 행동으로 연결된다.

인증 redirect는 앱 내부의 허용된 상대 경로만 사용해 open redirect를 막는다. 외부 URL을 `next`로 실행하지 않는다. access/refresh token과 provider raw error는 사용자 URL과 화면에 표시하지 않고 canonical 오류 이유로 바꾼다. callback server log도 token, provider `error_description`, Supabase 원본 오류를 기록하지 않고 canonical stage와 민감하지 않은 최소 진단 정보만 남긴다. 재전송이나 로그인 제한에는 남은 대기시간과 대체 행동을 보여주며, countdown 동안 중복 요청을 막는다. 등록 여부를 노출할 수 있는 계정 찾기·재설정 응답은 동일한 안전 문구를 사용한다.

로그인한 사용자의 프로필 조회 실패나 누락은 신규 가입 또는 가입 미완료로 간주하지 않는다. 사용자 화면은 재시도 가능한 일시적 이용 불가 상태를 보여주며, 일반 조회 경로에서 프로필을 자동 생성하지 않는다. 필수 이용약관과 개인정보처리방침은 관리자 원본에서 발행된 비-placeholder 문서가 둘 다 있을 때만 공식 문서와 동의 대상으로 인정한다. 문서가 누락되거나 조회에 실패하면 동의 완료와 다음 화면 이동을 차단한다.

### 목표·추천·문제 선택

1. 사용자는 목표 TOPIK 등급, 시험일과 학습 목표를 저장한다.
2. 홈에서 학습 현황, 최근 활동과 다음 추천을 확인한다.
3. 문제 유형 추천 또는 목록에서 쓰기 유형과 문제를 고른다.
4. 이전 기록이 있으면 현재 상태를 설명하고 처음부터 풀기·이어하기·피드백 보기 중 가능한 행동만 제공한다.
5. 추천 후보가 없거나 문제를 사용할 수 없으면 빈 상태의 이유와 문제 목록 등 대체 행동을 제공한다.

### 쓰기 51~54번

- 51·52번은 빈칸형 단답 입력, 53·54번은 장문 입력과 문제 자료를 제공한다.
- 51·52번 피드백은 제출한 두 빈칸 답안을 각각 `blank_1`, `blank_2` 평가와 대응해 전체 문자열로 보여 준다. 문장 안의 교정 지점은 빈칸별 점수에서 별도 제출 답안으로 나누지 않되, 문장별 첨삭 섹션에서는 독립된 교정 항목으로 계속 보여 준다.
- 51·52번의 작성 힌트는 현재 문항에 포함된 빈칸별 역할·문맥 기능·요구 답안 형태만 보여준다. 52번은 각 빈칸을 별도 입력으로 안내하며 두 입력을 하나의 통합 답안처럼 설명하지 않는다. 두 유형의 답안 입력 위에는 별도 제목·설명 없이 글자 수만 보여준다. 모든 문항에 같은 예시 표현을 고정 노출하거나 내부 검수용 문법 메타데이터와 정답 후보를 학습자 힌트로 사용하지 않는다.
- 54번 문제 카드는 canonical catalog의 제시문을 보존하고 그 안의 세 가지 작성 질문을 번호 목록으로 구분해 원문 순서대로 보여준다. 사용자 앱이 이를 `주제`·`배경`·`필수 포함 조건` 구획으로 다시 나누거나 중복 표시하지 않으며, 세 질문을 안전하게 구분할 수 없으면 원문 전체를 그대로 보여준다.
- 사용자가 지금 풀 문항은 admin이 검수·태깅·공개한 canonical 쓰기 catalog를 요청 시 직접 읽는다. 사용자 앱용 별도 문항 mirror와 주기적 동기화를 current-content 원천으로 사용하지 않는다.
- 현재 문항, 답안, 글자 수, 저장 상태와 최근 저장 시각을 사용자가 확인할 수 있어야 한다.
- 문제 유형에 맞는 필수 입력과 글자 수 조건을 충족해야 제출할 수 있다.
- 저장 중에도 입력을 잃지 않으며, 저장 실패 시 로컬 편집 상태를 유지하고 재시도를 제공한다.
- 브라우저 임시 복구본은 로그인 사용자와 문제·문항이 일치할 때만 같은 기기에서 단기간 복원에 사용한다. 기본 보관은 마지막 저장 후 24시간이며 최초 저장 후 7일을 넘기지 않는다. 이는 서버 백업, 장기 보관 또는 기기 간 동기화 보장이 아니다.
- 저장되지 않은 변경이 있는 이탈에는 `계속 작성`, `저장 후 이동`, `저장하지 않고 이동`처럼 결과가 분명한 선택을 제공한다.
- 사용자와 문제의 활성 초안은 하나로 수렴해야 하며, 반복 저장과 재시도는 중복 초안을 만들지 않아야 한다.
- 새 문항 시작을 나타내는 `fresh` 상태는 최초 저장 성공 뒤 한 번만 소비한다. 저장 뒤 URL과 이탈 방지 history 상태를 함께 정규화해 새로고침하면 방금 저장한 활성 초안을 다시 연다.

제출 전에는 답안 요약과 글자 수를 확인한다. 제출 요청은 한 번의 사용자 의도로 처리해 중복 제출을 막고, 서버 저장이 실패하면 작성 답안과 확인 단계가 유지되어야 한다. 성공한 제출본은 이후 수정되는 초안과 분리해 보존한다. 외부 처리 여부가 불명확한 timeout은 자동 재전송하지 않고 운영 확인이 가능한 상태로 격리한다. 이 멱등성 계약이 검증되지 않은 환경에서는 UI·server·DB가 제출을 차단하되 작성 답안은 보존한다.

사용자에게 `제출 완료`로 계산되는 기록은 제출과 분석·피드백이 모두 정상 완료된 경우뿐이다. 처리 중인 기록은 `분석 중`, 외부 API 오류·잘못된 응답·분석 실패 기록은 `분석 실패 · 다시 제출 필요`로 표시하며 완료 횟수와 완료 필터에서는 제외한다. 실패 기록은 삭제하지 않고 재시도와 운영 추적을 위해 보존한다. 이전 완료 기록이 있는 문제의 후속 재시도가 실패해도 기존 완료 기록은 유지한다.

### 분석·피드백·복구

1. 제출 후 분석 상태와 예상 대기를 보여준다.
2. 완료되면 문항 유형에 맞는 피드백으로 이동한다.
3. 지연되거나 상태 조회가 끝나도 제출 답안은 보존하며, 내 서재를 복구 표면으로 제공한다.
4. 분석 실패 재시도는 같은 제출본을 사용하고 새 제출을 중복 생성하지 않는다.
5. 사용자는 점수·총평·영역별 또는 문장별 피드백을 확인하고, 이전 답안 비교·다시 풀기·다음 문제 추천으로 이어간다.

분석 요청에는 사용자가 선택한 UI 언어(`ko`, `en`, `vi`)를 함께 전달한다. 분석 응답은 요청한 언어의 원문을 저장·표시하며, 클라이언트에서 임의로 자르거나 다시 번역하지 않는다. 현재 언어 선택은 새 분석 응답의 언어를 정하는 기능이고, 이미 저장된 과거 피드백을 다른 언어로 다시 번역하는 기능은 Future다.
피드백 요약과 상세 설명은 줄 수 제한이나 말줄임표로 내용을 숨기지 않고 기본 상태에서 전체 문구를 보여준다.

실제 AI가 deferred인 동안 mock 결과나 분석 상태를 실제 provider 처리로 표현하지 않는다.

### 기관 초대 알림

- 사용자가 기관 초대 알림을 열면 다른 화면으로 이동하기 전에 초대 내용을 모달로 확인한다.
- 모달에서 선택할 수 있는 행동은 `닫기`와 `수락`뿐이며, 별도의 거부 행동은 제공하지 않는다.
- 닫기는 모달만 닫고 초대 응답을 보내지 않는다. 알림을 읽은 상태와 초대를 수락한 상태는 서로 별개다.
- 수락하면 초대 응답을 보내고, 완료·만료·회수·이미 처리됨과 같은 결과를 사용자가 이해할 수 있는 상태로 안내한다.
- 기관 코드는 모달에 표시하고, 확인할 수 없으면 대체 문구를 보여 준다. 응답할 초대 정보가 유효하지 않으면 수락은 막되 닫기는 계속 허용한다.
- 기관 초대 알림 payload에 유효한 `expires_at`이 있으면 알림 목록에 `Asia/Seoul` 날짜 기준 `D-n` 또는 만료 상태를 표시하고, 모달에는 사용자 locale 형식의 만료일을 표시한다. 같은 날짜에 만료되는 초대는 만료 시각 전까지 `D-0`이다.
- `expires_at`이 현재 시각 이하이거나, 수락 직전 재확인에서 만료됐거나, 응답 API가 만료를 확정하면 수락을 비활성화하되 닫기는 계속 허용한다. 응답 API가 반환한 최종 상태가 화면의 사전 계산보다 우선한다.
- `expires_at`이 없거나 유효하지 않으면 생성 시각에 고정 기간을 더해 만료를 추정하지 않으며, 만료 표시 없이 기존 초대 흐름을 유지한다. 일반 알림에는 초대 만료 정보를 표시하지 않는다.

정확한 알림 payload와 응답 API 계약은 Supabase 계약 문서와 현재 source/tests가 소유한다.

#### 결정 기록 (2026-07-14)

- 결정 이유: 사용자가 초대의 남은 유효기간과 수락 가능 여부를 목록과 모달에서 즉시 이해할 수 있어야 한다.
- 근거: 알림 payload의 canonical `expires_at`, 수락 RPC의 최종 상태, 현재 source와 단위·desktop/mobile E2E 테스트를 기준으로 한다.
- 검토한 대안: `created_at + 고정 기간` 추정은 실제 만료 계약과 어긋날 수 있어 제외했고, v13 DB에 만료일을 중복 저장하거나 수락 RPC를 변경하는 방안은 이번 사용자 앱 표시·동작 제한 범위를 넘어 제외했다.

### 내 서재와 복습

- 완료된 제출·피드백, 진행 중 초안, 저장 문제를 구분한다.
- 검색·필터·정렬 결과와 항목 상태를 명확히 보여준다.
- pending/analyzing/failed 상태도 사라지지 않고 상태 확인 또는 복구 행동으로 연결된다.
- 삭제·재도전처럼 되돌리기 어려운 행동은 대상을 분명히 하고 필요한 확인을 거친다.

### PDF 내보내기

- 인증 사용자는 자신이 접근할 수 있는 쓰기 결과를 PDF로 생성하고 저장된 파일을 다시 내려받을 수 있다.
- 제출 PDF는 제출 당시 고정된 문제 snapshot에서 문제 번호·제목·지문·학습자에게 공개된 자료를 재구성한다. 내보내기 시점의 현재 문항이나 외부 API를 다시 조회해 과거 문제 내용을 바꾸지 않는다.
- 문제 snapshot을 확인할 수 없으면 현재 문항으로 추정하지 않고 제출 당시 문제 정보를 확인할 수 없다는 안내를 PDF에 남긴다.
- 기본 quota는 사용자별·쓰기 문제별 한 달 3회이며 기간 경계는 `Asia/Seoul`의 매월 1일 00:00이다.
- 한 PDF에 같은 문제가 여러 번 포함돼도 distinct 문제 하나로 한 번만 계산한다.
- 대상 문제는 서버가 제출·리포트 관계에서 결정하며 browser가 임의로 quota 대상을 선택하지 않는다.
- 새 생성은 quota를 먼저 예약하고 성공 시 확정한다. 생성 실패는 예약을 해제해 횟수를 소비하지 않는다.
- PDF 생성 요청은 인증과 요청 형식 검증 뒤 `queued`로 기록하고 `ready` 또는 `failed`로 마감한다. 기술 실패, quota 거절, browser print 전달은 서로 다른 결과로 분류한다.
- 저장된 PDF의 재다운로드는 새 생성이 아니므로 횟수를 소비하지 않는다.
- 서버 PDF와 browser print 경로는 같은 quota 검사를 거치며 fallback으로 우회할 수 없다.
- 초과는 시스템 장애가 아닌 중립적 제한 안내로 표시하고 limit, used, remaining, reset 시점과 period 단위를 제공한다.
- 정책 변경과 사용자·그룹·전체 reset은 별도 admin 소유 앱의 운영 범위다. v13은 적용된 정책을 읽고 집행만 한다.

## 4. 공통 UX 수용 기준

모든 user-facing 화면은 필요한 상태를 같은 layout 안에서 다룬다.

| 상태 | 사용자 약속 |
| --- | --- |
| Loading | 무엇을 기다리는지 알리고 중복 행동을 막는다. |
| Empty | 데이터가 없는 이유와 가능한 다음 행동을 보여준다. |
| Success | 무엇이 저장·제출·변경됐는지 알려준다. |
| Error | 입력을 보존하고 이해 가능한 이유, 재시도 또는 안전한 이동을 제공한다. |
| Disabled | 사용할 수 없는 이유를 버튼 주변에서 알 수 있게 한다. |

사용자 오류 안내에는 provider·데이터베이스·SQL·token·stack·request body 같은 내부 원인을 표시하지 않는다. 일반 서비스, 필수 정보, 학습 자료의 세 범주에 맞는 넓은 안내와 재시도·뒤로가기·기록 확인 같은 안전한 다음 행동만 제공한다. 상세 원인은 허용된 코드와 최소 수치만 사용하는 내부 운영 이벤트로 분리한다.

### 화면 뒤로가기와 방문 기록

화면 안의 뒤로가기 버튼은 현재 작업 흐름에서 약속한 화면으로 이동하는 기능이며, 브라우저·휴대폰의 자체 뒤로가기는 사용자가 실제로 방문한 기록을 따라가는 기능이다. 화면 버튼은 떠난 상세·작성 화면이 브라우저 뒤로가기에 다시 나타나지 않도록 현재 기록을 교체하고, 일반 메뉴·CTA는 기존처럼 새 방문 기록을 쌓는다.

| 화면 버튼 | 목적지 |
| --- | --- |
| 쓰기 51~54번 | 검증된 유입 화면. 없거나 안전하지 않으면 문제 목록 |
| 단답·장문 피드백 | 내 서재 |
| 비교 리포트 | 현재 제출의 피드백 |
| 서재 문제 목록 | 내 서재 |
| 결제 안내 | 다음 문제 추천에서 들어왔으면 해당 화면, 직접 진입하거나 안전하지 않으면 홈 |

쓰기 복귀 주소는 홈, 연습 하위 화면, 내 서재와 서재 문제 목록, 현재 피드백·비교 리포트만 허용한다. 허용된 문제 목록의 검색·필터·정렬·페이지와 query/hash는 보존한다. 외부 URL, `//` 또는 역슬래시 변형, 인증·API 경로, 다른 쓰기 화면, 중첩 복귀 주소, 알 수 없는 경로는 실행하지 않고 위 표의 기본 목적지를 사용한다. 결제 안내 복귀 주소는 현재 실제 유입처인 다음 문제 추천만 허용한다.

저장되지 않은 쓰기 답안이 있을 때 화면 뒤로가기와 일반 링크는 같은 이탈 확인을 거치되, 사용자가 승인한 뒤에는 각 버튼이 약속한 이동 방식을 유지한다. 화면 버튼으로 이동할 때는 이탈 방지용 임시 방문 기록을 먼저 제거한 뒤 목적지로 교체해, 이후 브라우저 뒤로가기로 방금 떠난 작성 화면이 다시 나타나지 않게 한다. 브라우저 자체 뒤로가기는 이와 분리해 실제 방문 기록을 따른다.

- 데스크톱과 모바일에서 핵심 정보, 입력, primary action이 겹치거나 가로로 넘치지 않아야 한다.
- keyboard focus, form label, icon-only control 이름을 제공하고 색만으로 상태를 전달하지 않는다.
- 긴 한국어 지문과 피드백은 읽기 폭과 줄 간격을 유지한다.
- 주요 기능은 한국어·영어·베트남어 UI를 지원한다. 문서의 실제 언어를 root `lang`에 표시하고 `translate="no"`와 번역 서비스용 `notranslate` 메타데이터로 브라우저의 자동 번역을 막아, 앱의 언어 설정과 분석 응답이 이중 번역되지 않게 한다. 번역되지 않는 학습 콘텐츠는 UI 언어가 바뀐 것처럼 오해시키지 않는다.

## 5. 데이터·보안 불변 조건

- 학습자 데이터는 인증 사용자 본인 소유 범위로 제한한다.
- 제출본, 피드백, 초안, 추천, 서재, 학습 이벤트와 export의 관계가 끊기지 않아야 한다.
- 초안 저장, 최종 제출, 비교·재시도, quota는 중복 요청과 네트워크 재시도에 안전해야 한다.
- 프로필의 권한·요금제·기관 연결 같은 보호 필드는 일반 사용자가 직접 바꿀 수 없다. 계정 탈퇴를 위한 본인의 `active → deleted` 전이는 허용하며, 복구와 다른 status 변경은 운영 경계다.
- service-role 작업은 server-only 경계에서 최소 범위로 실행하고 browser에서 호출하거나 노출하지 않는다.
- 탈퇴는 사용자 접근을 즉시 막는 소프트 삭제와 30일 복구 유예를 기본 제품 약속으로 한다. 실제 영구 삭제·보존 정책은 운영 소유 절차와 migration 계약을 따른다.

세부 데이터 계약은 `docs/supabase/`, 실제 DB 동작은 `supabase/migrations/*.sql`을 따른다.

## 6. 성공 기준

- 사용자가 홈에서 다음 학습 행동을 선택할 수 있다.
- 추천 또는 목록에서 쓰기 문제를 시작할 수 있다.
- 작성 중 입력을 잃지 않고 제출을 완료할 수 있다.
- 피드백 또는 대기 상태를 내 서재에서 다시 찾을 수 있다.
- 다시 풀기와 다음 문제로 학습이 이어진다.
- 인증 오류, 저장·제출·분석 실패와 quota 초과에서 막히지 않고 안전한 다음 행동을 찾을 수 있다.
