## 사용자에게 보이는 실패 원칙

- 오류 문구는 사용자가 지금 무엇을 할 수 있는지와 입력·저장 상태를 넓고 안전한 범주로 알린다.
- DB 이름, 정책 이름, 내부 상태값, provider 응답, stack trace, 원본 오류 메시지와 인증·권한 판정 근거는 화면·URL·브라우저 로그에 노출하지 않는다.
- 성공이 확인되지 않으면 성공으로 표시하지 않는다. 재시도가 중복 저장·중복 제출을 만들 수 있으면 자동 재시도하지 않는다.
- 문의에 식별자가 필요하면 사용자·환경·내부 원인을 포함하지 않는 별도 비식별 문의 코드만 사용한다.

| 영역 | 실패 시 사용자 계약 |
| --- | --- |
| 답안 저장 | 현재 입력을 유지하고, 기기 임시 복구 여부와 서버 동기화 실패를 구분해 알린다. |
| 약관 | 필요한 문서와 버전을 확인할 수 없으면 동의·가입 완료를 진행하지 않고 재시도를 제공한다. 사용자가 보지 않은 새 버전에 동의한 것으로 기록하지 않는다. |
| 프로필 | 저장 확인 전에는 완료로 표시하지 않고 입력을 유지한다. 세션·소유권을 확인할 수 없으면 변경을 막는다. |
| 문제·파일·내보내기 리소스 | 올바른 사용자·버전·파일임을 확인할 수 없으면 오래되거나 다른 리소스를 대신 표시하지 않는다. 기존 기록을 보존하고 안전한 재시도를 제공한다. |

## IndexedDB 임시 복구본

IndexedDB 복구본은 같은 브라우저에서 충돌·탭 종료·일시적 통신 실패 뒤 입력을 되찾기 위한 임시 사본이다. 서버 백업, 장기 보관, 기기 간 동기화 또는 제출 증명이 아니다.

- 사용자·문제·정본 버전·자료 형식 버전으로 범위를 나누고, 답안, 서버가 확인한 내용의 hash, 임시 제출 의도 식별자와 복구에 필요한 최소 metadata만 저장한다. metadata에는 현재 형식인 `schemaVersion=1`, 최초 저장 때 생성해 이후 덮어쓰기·재시도·복원에서도 바꾸지 않는 `firstStoredAt`, 마지막으로 로컬 저장에 성공한 `savedAt`을 포함한다. 명시적 migration도 기존 `firstStoredAt`을 보존한다.
- 크기는 IndexedDB key, metadata와 value 전체를 `{ key, metadata, value }` 형태의 canonical JSON으로 직렬화한 뒤 `TextEncoder`로 얻은 UTF-8 byte 길이로 계산한다. record 하나는 256 KiB 이하여야 한다.
- `schemaVersion`이 현재 버전보다 크거나 지원하지 않는 미래 형식이면 복원을 거부하고 격리한다. 이전 앱은 이를 migration하거나 삭제하지 않는다. 해당 버전을 지원하는 새 앱의 명시적 migration, 그 형식으로 검증한 만료 처리 또는 사용자의 직접 삭제에서만 정리할 수 있으므로, 현재 앱은 미래 버전을 보존한다.
- 현재 형식이지만 invalid·corrupt·oversize인 record는 복원에 사용하지 않고 안전하게 격리한다. 소유 범위를 확인한 뒤 만료, 서버의 동일 내용 동기화·제출 확인, 사용자 직접 삭제 또는 명시적 repair/migration으로 폐기 가능성이 확인된 경우에만 삭제한다. 소유 범위나 안전한 삭제 조건을 확인할 수 없으면 격리 상태로 보존한다.
- 기본 expiry는 `min(최신 savedAt + 24시간, firstStoredAt + 7일)`이다. 사용자가 명시적으로 연장해도 `firstStoredAt + 7일`을 절대 넘지 않으며, 반복 연장·덮어쓰기·재시도로 `firstStoredAt`이나 7일 상한을 갱신하지 않는다.
- 전체 저장소와 사용자별 고정 용량 상한은 이 정책에서 임의로 만들지 않는다. quota 부족이나 쓰기 실패 때 자동 정리 후보는 검증된 현재 형식 중 retention이 실제로 끝난 record와 서버의 동일 내용 동기화 성공이 확인된 record로 제한한다. 그중 가장 오래된 만료 record부터, 이어서 가장 오래된 동기화 확인 record부터 정리한다. 아직 retention 안에 있는 현재 작성 record와 서버 동기화 또는 제출이 확인되지 않은 다른 record는 사용자 확인 없이 삭제하지 않는다.
- 안전한 후보를 정리해도 저장할 수 없으면 현재·다른 미동기화 record를 삭제하지 않고 저장을 실패시킨다. `저장이 지연되고 있습니다. 작성 내용은 이 기기에 임시 보관되지 못했습니다. 잠시 후 다시 시도해 주세요.`라고 알리며 내부 원인은 노출하지 않는다.
- 쓰기 화면 시작 때 현재 앱이 정확히 검증할 수 있는 현재 형식 record의 만료 여부를 검사하고, retention이 끝난 record는 서버 동기화 여부와 관계없이 조건부 삭제한다. 삭제 직전 다른 탭이 내용을 바꿨다면 최신 record는 지우지 않는다. retention 안에서는 서버가 같은 내용의 저장을 확인했을 때, 제출이 확정되어 결과 식별자를 확보했을 때 또는 사용자가 폐기를 직접 선택했을 때 삭제할 수 있다. 로그아웃·계정 삭제·사용자 전환 중 retention 안의 미동기화 record 삭제가 필요하면 그 영향을 사용자에게 확인받는다.
- `clearForLogout`은 현재 앱이 검증할 수 있고 서버 동기화가 확인된 현재 형식 record만 정리한다. 미동기화 current record와 미래 형식 record는 보존한다. `clearForAccountDeletion`은 사용자가 계정 삭제를 확정한 뒤 호출하는 직접 폐기 API이므로 명시된 사용자 소유의 current·future record를 정리할 수 있으며, 일반 로그아웃이나 사용자 전환에서 대신 호출하지 않는다.
- 프로필 화면과 전역 프로필 메뉴의 로그아웃은 서버 sign-out 요청 전에 `clearForLogout`을 best-effort로 실행한다. 정리 실패가 로그아웃을 막거나 원본 오류를 사용자에게 노출하지 않는다.
- 회원 탈퇴는 서버가 계정 삭제 성공을 최소 응답으로 확정한 뒤에만 `clearForAccountDeletion`을 호출하고 로그인 화면으로 이동한다. 서버가 실패를 응답하거나 네트워크가 끊기면 로컬 복구 record를 지우지 않는다. 서버 삭제 성공 뒤 로컬 정리만 실패하면 모달을 닫지 않고 넓은 오류 안내와 재시도를 제공하며, 재시도에서는 서버 삭제 요청을 반복하지 않고 로컬 정리만 실행한다.
- 계정이 확인되지 않는 상태에서는 복구본 내용을 화면에 먼저 펼치지 않는다. 현재 사용자와 항목의 소유 범위가 일치한 뒤에만 복원 선택지를 보이며, 불일치 record는 노출·복원하지 않고 격리해 위의 안전한 삭제 조건을 적용한다.
- 로컬과 서버 내용이 다르면 시각·hash·정본 버전을 비교해 `기기 사본 복원`, `서버 내용 유지`, `내용 비교`를 명시적으로 선택하게 한다. 자동 병합이나 조용한 덮어쓰기는 금지한다.
- 다른 탭의 변경을 감지하면 저장 경쟁을 알리고 한 탭의 내용을 자동으로 승자로 정하지 않는다.
- 제출 응답을 잃은 경우 임시 의도 식별자로 서버의 사용자 소유 상태를 다시 확인한다. 상태가 모호하면 같은 제출을 자동 전송하지 않는다.
- `저장하지 않고 이동`은 서버 저장을 생략한다는 뜻이다. 현재 브라우저의 유효한 임시 복구본은 retention이 끝날 때까지 best-effort 안전망으로 남을 수 있으므로, 화면에서 작성 내용이 즉시 완전히 삭제된다고 안내하지 않는다.

## 상태 표현

기기 안전과 서버 동기화는 별도 상태로 보여준다. 예: `이 기기에 임시 저장됨`, `서버 저장 중`, `서버 저장 완료`, `서버 저장 실패—기기 사본 있음`, `충돌 확인 필요`. 서버 저장 시각만으로 현재 입력의 복구 가능성을 주장하지 않는다.

## 비범위와 한계

- service worker, 오프라인 탐색, 백그라운드 동기화 큐, 다중 기기 병합, CRDT, 전체 변경 이력은 이 정책의 범위가 아니다.
- 브라우저 사본은 공용 기기와 XSS 위험을 없애지 못한다. 최소 수집, 짧은 TTL, 즉시 삭제를 적용해도 백업 보장으로 표현하지 않는다.
