🏗️ 설계도 vs 실제 건물

설계도는 "이런 방을 만들자"고 적어둔 마이그레이션 파일이고, 실제 건물은 진짜 운영되는 데이터베이스입니다. 설계도에는 "약관 보관실", "문제 만료 표시 선반", "문제 목록 자동 안내판" 같은 방이 그려져 있었는데, 실제 건물에는 그 방들이 아직 안 지어져 있었습니다. 그런데 입주민(앱 화면)은 이미 그 방을 쓰려고 만들어져 있었죠. 그래서 "있어야 할 안내판이 비어 있는" 반쪽짜리 상태였습니다.

📒 멈춰버린 공사 기록부

건물에 어떤 공사를 했는지 적는 공사 기록부(데이터베이스의 schema_migrations 추적표)가 중간에 멈춰 있었습니다. 그래서 어떤 공사는 됐고 어떤 공사는 안 됐는지 아무도 정확히 모르는 상태였어요. 누군가 기록부에 안 적고 공사를 몇 개 했고, 그 와중에 몇 개를 빠뜨린 것이 이번 어긋남의 뿌리였습니다.

🛎️ 옛 안내도를 든 안내데스크 (가장 까다로웠던 함정)

건물 입구의 안내데스크(PostgREST라는 데이터 중개 계층)가 옛날 안내도를 보고 "약관 보관실 있습니다"라고 안내했습니다. 그래서 처음엔 저도 "약관 방은 이미 있구나" 하고 넘어갔는데, 실제로 가보니(데이터베이스에 직접 물어보니) 그 방은 존재하지 않았습니다. 안내데스크의 낡은 안내도에 속을 뻔한 부분을 끝까지 확인해 바로잡았습니다.

항목현재 상태왜 보류
topic_category_code·review_workflow_status의 "코드값" 확정 PROPOSED 관리자(topik-ai) 쪽 코드값이 아직 한글 라벨뿐이라, 정식 코드 확정 전까지는 컬럼만 두고 값 매핑은 고정하지 않음(검증 규칙 CHECK 없음).
약관 문서 실제 내용 빈 상태 약관 "보관실"(테이블)은 만들었지만, 그 안에 넣을 실제 약관 문서는 관리자가 작성·발행해야 함. 화면은 발행된 문서를 읽음.
회원 탈퇴(withdraw) 상태 매핑 UNMAPPED 탈퇴가 소프트삭제/개인정보삭제/복구 중 무엇인지 의미가 미확정 → 쓰기 매핑 금지(통합 설계서 D-F).
관리자(topik-ai) 실제 연결·UI LATER 이 저장소는 사용자 화면 전용. 관리자 연결은 사용자 화면 완료 후 별도 단계(스키마는 이미 정합 준비됨).
코드의 임시 우회(as any) 제거 후속 types.ts 보강으로 제거 가능해졌으나, 결제/알림 데이터 모듈의 캐스트 정리는 별도 후속 정리 작업.

10추가 작업 — v13 "관리자 별관" 전체 철거 (방향 전환)

🔄 무엇이 바뀌었나 (데이터 흐름)

관리자(topik-ai)가 외부(제3자) API에서 "검수가 이미 끝난" 문제를 받아 → 노출 여부(공개/비공개)만 적용해 → Supabase 데이터베이스에 저장하고, v13은 그 데이터를 "읽기만" 합니다(read-only). 따라서 v13 안에서 문제를 편집·검수하거나 관리자가 회원·조직을 관리하는 기능을 둘 이유가 없어집니다. 그래서 v13에 남아있던 "관리자 별관"을 통째로 철거했습니다.

[외부 3자 API] → [관리자(topik-ai): 받기 + 노출(공개/비공개) 적용] → [Supabase DB 저장] → v13: 읽기만 → [사용자]

🏚️ 잠가두었던 "관리자 별관"을 헐다

v13의 관리자 코드는 사실 예전에 "전부 v13에 만들자"던 시절의 잔재였습니다. 본관(사용자 앱)과 통로가 없고 (사용자 코드가 이 별관을 부르는 곳 0개), 관리자 열쇠가 있어야만 들어가는 잠긴 별관이었죠. 진짜 관리동은 옆 부지(topik-ai)에 따로 짓기로 했고, 이 별관은 "헐지 말지는 주인 결정"으로 남겨둔 상태였습니다. 이번에 주인(고객님)이 철거를 결정했고, 문 안의 배선(DB 함수)과 건물(코드)을 한 세트로 깔끔히 헐었습니다 — 단, 건물 전체를 떠받치는 기둥(공통 권한·감사 토대)은 그대로 두었습니다.

구분대상처리
🗑️ 코드 삭제관리자 화면/컴포넌트/라이브러리(routes·components·lib·guard) + 네비 메뉴 + 관련 테스트삭제 (파일 ~36개)
🗑️ DB 삭제문제 쓰기·사용자관리·감사조회 admin RPC 11개 + 조직 테이블 4개 + 조직 헬퍼 2개drop (마이그레이션 20260609130000)
🟢 보존(기둥)app_role(권한), admin_audit_logs(감사표), private.is_*_admin(보안정책 헬퍼·정책 12개가 의존)유지

🟥 철거 전

  • admin RPC: 11개
  • 조직 테이블: 4개 + 헬퍼 2개
  • 관리자 화면 코드/라우트/네비: 존재
  • 검수 메모(②): 적용돼 있었음
➡️

🟩 철거 후

  • admin RPC: 0개 ✅
  • 조직 테이블/헬퍼: 0개 ✅
  • 관리자 코드 전부 삭제, 네비에서 사라짐 ✅
  • 기둥(app_role·admin_audit_logs·is_*_admin) 그대로 ✅

📌 이 철거가 바꾸는 것 (통합 설계서 전제)

원래 통합 설계서(admin-integration-plan.md)는 "문제는 topik-ai 관리자가 저작·검수"하고 "topik-ai가 v13의 admin RPC를 재사용"한다는 전제였습니다. 외부-API 모델 + admin 철거로 그 두 전제는 무효가 되어, 문제 영역은 외부-API 기준으로 재설계가 필요합니다. (회원·결제 overlap은 영향 없음.) 설계서 맨 위에 PIVOT 메모를 박아뒀습니다.
