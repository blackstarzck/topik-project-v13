4. 진짜 "결정이 필요한" 9가지 (= 당신 몫)

버그가 아니라 "이 기능/데이터를 만들까 말까"를 정해야 하는 일입니다. 2026-06-08 기준 9가지 모두 확정했습니다 — 아래 각 항목의 확정(FINAL) 줄이 최종 선택입니다.

“객관 제안”은 검토 에이전트의 의견(참고용)이고, “확정(FINAL)”이 실제 결정입니다. #2·#4는 새 스키마가 필요하지만 둘 다 관리자 앱이 소유한 공유 엔티티라, 만들기 전 소유자 승인 + admin 데이터 계약(topik-ai/docs/specs/admin-data-contract.md) 이름 맞춤이 필요합니다(이 저장소엔 그 계약 파일이 없음). 그래서 결정은 끝났어도 마이그레이션은 아직 쓰지 않습니다.

1
추천 규칙표
약점 → 문제유형 매핑·가중치

왜 필요? 지금은 추천 결과를 저장할 수는 있지만, “문법이 약하면 51번을 먼저 줄지, 구조가 약하면 54번을 줄지” 같은 운영 규칙표는 없습니다.

선택지

  • A. 당분간 현재 추천 결과와 임시 규칙만 사용
  • B. 문서나 설정 파일로 간단한 규칙표를 먼저 둠
  • C. DB/CMS에서 운영자가 직접 바꾸는 추천 규칙표를 만듦
객관 제안: B. 간단한 규칙표부터 시작. 추천 이유를 설명할 수 있고, 새 DB를 만들지 않아도 됩니다.
확정(FINAL): 보류. 추천 규칙표는 나중에 결정합니다.
미뤄도 되나? 일부 가능. 다만 “왜 이 문제가 추천됐는지”를 화면에 보여주려면 최소 규칙은 정하는 편이 좋습니다.

2
약관/개인정보 동의 기록
버전·공개일·동의 시각

왜 필요? 가입 화면에는 약관 동의가 있지만, 사용자가 어떤 버전에 언제 동의했는지 저장하는 구조는 아직 없습니다.

선택지

  • A. 정적 약관만 보여주고 동의 기록은 저장하지 않음
  • B. 약관 버전, 공개일, 동의 시각만 최소 저장
  • C. 약관 변경 이력, 재동의, 제출 동의까지 모두 이력으로 저장
객관 제안: B. 실제 사용자 운영 전에는 최소 동의 이력을 남기는 쪽이 안전합니다.
확정(FINAL) — B: 약관·개인정보 문서를 버전별로 저장하고, 각 사용자가 어떤 버전에 언제 동의했는지를 기록합니다. (질문에 대한 답: 네, "문서를 버전별로 저장 + 동의 이력 보관"이 맞습니다.) 관련 테이블은 아직 없습니다 — 마이그레이션 30개를 전수 확인한 결과 약관 버전 테이블·사용자 동의 이력 테이블·profiles 동의 컬럼이 모두 부재(확인됨). 다만 약관·정책은 관리자 앱이 소유한 영역(admin 계약의 operation_policies · requiresConsent)이라, 새 테이블을 이 저장소에서 임의로 만들지 않고 소유자 승인 + admin 계약 이름 맞춤을 거쳐 설계합니다. 사용자 승인 후 마이그레이션 작성·검수 완료(파일 #31, 적대적 검수 READY_TO_APPLY; 실제 DB 반영은 Docker 환경에서 적용). 상세는 아래 5번 후속 브리프.
미뤄도 되나? 내부 테스트는 가능. 실제 회원가입을 받기 전에는 결정해야 합니다.

작문 유형별 결제 잠금
51~54번 무료/유료 범위

왜 필요? 어떤 쓰기 유형을 무료로 둘지, 어떤 유형을 유료로 잠글지 정해야 페이월 문구가 흔들리지 않습니다.

선택지

  • A. 모든 작문 유형을 일단 무료로 둠
  • B. 화면에는 “유료 예정” 안내만 보여주고 실제 잠금은 하지 않음
  • C. 51~54번 유형별로 실제 결제 잠금을 연결함
객관 제안: A 또는 B. 현재 문서상 결제는 보류 범위라 실제 잠금은 아직 하지 않는 것이 맞습니다.
확정(FINAL): A. 모든 작문 유형을 일단 무료로 둡니다.
미뤄도 되나? 예. 결제 정책과 제공자를 정하기 전까지는 미루는 편이 안전합니다.

4
문제 “만료”의 의미
문제 자체인지, 추천 묶음인지

왜 필요? “만료”가 문제 자체를 못 보게 한다는 뜻인지, 오래된 추천만 숨긴다는 뜻인지에 따라 보관함과 제출 이력의 동작이 달라집니다.

선택지

  • A. 추천만 만료됨. 문제와 과거 제출은 계속 볼 수 있음
  • B. 문제 자체가 만료되어 더 이상 노출되지 않음
  • C. 사용자가 풀 수 있는 기간만 만료됨
객관 제안: A. “추천 만료”로 좁히는 것이 가장 안전합니다. 문제 공개 상태와 보관 이력은 따로 유지할 수 있습니다.
확정(FINAL): 문제 만료 기준은 아직 정하지 않습니다. 대신 problems에 문제 자체의 상태·만료를 표현할 전용 컬럼을 별도로 둡니다(원하시는 방향 반영). 현재 problems에는 공개 상태(publish_status)·검수 상태(review_status)·노출 범위(visibility)는 있으나 문제 전용 만료 컬럼은 없음(확인됨 — expires_at은 추천 묶음 recommendation_runs에만 있고 문제와 무관). 단 problems는 관리자 앱이 소유한 공유 문제은행(admin 계약의 assessment_questions)이라, 컬럼 추가도 임의로 하지 않고 소유자 승인 + admin 계약 이름 맞춤을 거칩니다. 기준이 미정이므로 컬럼만 두고 자동 만료 로직은 보류. 사용자 승인 후 마이그레이션 작성·검수 완료(파일 #32; 실제 DB 반영은 Docker 환경에서 적용).
미뤄도 되나? 화면에 “만료” 문구를 안 쓰면 미룰 수 있습니다. 문구를 쓸 거면 먼저 정해야 합니다.

보관함 복습세트 / 폴더 / 공유
기본 보관 vs 고급 정리 기능

왜 필요? 현재 보관함은 저장, 태그, 메모 중심입니다. 폴더, 복습세트, 공유 링크는 별도 구조가 필요합니다.

선택지

  • A. 현재처럼 태그와 메모만 사용
  • B. 개인용 폴더/복습세트만 추가
  • C. 공유 링크나 공개 보관함까지 추가
객관 제안: A로 유지. 필요가 커지면 B를 다음 단계로 추가. C는 개인정보와 답안 공개 위험이 커서 보류가 맞습니다.
확정(FINAL): A. 현재처럼 태그와 메모만 사용합니다.

인증·보안 로그
로그인 시도·재발송·콜백 실패

왜 필요? 사용자가 “메일이 안 왔다”, “로그인이 안 된다”고 말할 때 원인을 확인하려면 최소 기록이 필요합니다.

선택지

  • A. Supabase 기본 로그만 사용
  • B. 앱에는 주요 실패/재발송 이벤트만 최소 기록
  • C. 보안 감사용 상세 로그를 별도 테이블로 운영
객관 제안: B. 이메일, 오류 종류, 시간 정도만 최소로 남기고 토큰이나 원문 오류는 저장하지 않습니다.
확정(FINAL): A. 별도 앱 DB 로그를 만들지 않고 Supabase 기본 로그만 사용합니다.
미뤄도 되나? 내부 테스트는 가능. 실제 가입/로그인 운영 전에는 최소 정책을 정하는 편이 좋습니다.

선택지

  • A. 코드 안의 고정 문구로 관리
  • B. 번역/문구 파일로 관리
  • C. 별도 CMS에서 운영자가 수정
객관 제안: B. 문구 파일부터 시작. CMS는 권한, 검수, 배포 흐름까지 필요해서 지금은 큽니다.
확정(FINAL): B. 번역/문구 파일로 관리합니다. 별도 CMS는 만들지 않습니다.
미뤄도 되나? 예. 문구 변경이 잦아질 때 CMS로 확장하면 됩니다.
