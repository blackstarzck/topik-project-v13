2. QA가 지적한 결함 9건 — 무엇이 문제였고 어떻게 고쳤나

2-1. 배포를 막던 문제 (가장 급했던 것)

이 앱에는 "학습자용 앱 코드에 관리자 전용 단어가 섞이면 안 된다"는 자동 감시 장치가 있습니다. 그런데 약관 화면 코드에 붙은 설명 메모(주석) 속에 관리자 쪽 데이터 이름이 적혀 있어서 이 장치가 경보를 울렸고, 배포가 차단됐습니다. 실제로 관리자 데이터에 접근한 것은 아니어서, "이 메모는 설명일 뿐"이라고 감시 장치의 예외 목록에 정식으로 등록해 해결했습니다. 검사는 이제 통과합니다.

2-2. 사용자 눈에 보이던 문제

문제 사용자가 겪던 일 원인과 조치 확인
약관 화면에 기호 노출 약관 본문에 <div>, <br>, ## 같은 코드 기호가 그대로 보였습니다. 관리자가 작성한 약관 본문이 두 가지 표기법(HTML과 Markdown)을 섞어 쓰는데, 화면에 그려주는 변환기가 한 가지씩만 처리할 수 있었습니다. 섞인 본문도 처리하도록 변환기를 고쳤습니다. 보안 필터는 그대로 유지했고, 공격 시도가 통하지 않는 것도 테스트로 확인했습니다. 실제 화면 확인
약관 화면에 특수 표기 노출 (추가 발견) 태그는 사라졌는데 &gt;, &nbsp; 같은 표기가 글자로 보였습니다. 변환기가 이미 올바르게 쓰인 특수 표기(HTML 엔티티)까지 한 번 더 감싸 버려서 생긴 문제입니다. 올바른 표기는 그대로 두도록 고쳤습니다. 실제 화면 확인 (0건)
차트 크기 경고 작은 화면에서 차트가 크기를 못 잡을 수 있다는 경고가 반복됐습니다. 차트를 담는 상자에 폭 기준이 없어서 생긴 문제입니다. 정상 동작하던 차트와 같은 방식(초기 크기 지정 + 폭 100%)으로 통일했습니다. 코드 검사 통과
첫 화면(랜딩) 빌드 경고 사용자가 겪는 문제는 없었고, 빌드할 때마다 "이 페이지는 미리 만들 수 없다"는 경고가 남았습니다. 첫 화면 버튼이 로그인 여부에 따라 달라지는 것은 의도된 동작이라고 코드에 명시했습니다. 경고가 사라졌습니다. 빌드 로그 확인 (경고 0건)

2-3. 자동 테스트가 고장 나 있던 문제

아래 4건은 제품이 아니라 테스트 쪽이 문제였습니다. 모두 고쳐서 실제 브라우저 실행으로 통과를 확인했습니다.

화면 테스트가 실패한 진짜 이유 조치
비밀번호 재설정 테스트 브라우저가 영어 설정으로 열려서 화면이 영어로 나왔는데, 테스트는 한국어 글자를 찾고 있었습니다. 테스트 브라우저를 한국어로 고정했습니다.
결제 안내(구독 시작) 결제 기능은 아직 보류 상태라 "안내 가능한 플랜 없음"이 정상인데, 테스트는 플랜 목록만 정답으로 알고 있었습니다. 빈 상태와 플랜 목록 둘 다 정상으로 인정하도록 테스트를 고쳤습니다. (제품 방향은 오너 확인을 받았습니다)
다시 풀기 안내창 "다시 풀기" 버튼은 이전에 풀던 기록이 있어야 나타나는데, 테스트 계정에 기록이 하나도 없었습니다. 테스트가 시작할 때 "풀다 만 문제"를 스스로 만들고 끝나면 지우게 했습니다.
첨삭 결과(피드백) 화면 테스트용 데이터를 만들다 중간에 실패하면 원인을 알기 어려운 상태로 죽었습니다. 데이터 준비 과정을 튼튼하게 만들고, 실패하면 원인을 바로 알려주도록 했습니다.

2-4. 전체 자동 테스트가 15분 안에 못 끝나던 문제

전체 브라우저 테스트는 한 번에 돌리면 60~80분이 걸립니다. 15분 제한과는 구조적으로 맞지 않아서, 6조각으로 나눠 돌리는 절차를 만들어 문서에 남겼습니다. 이 방식으로 실제로 끝까지 완주했습니다.

3. 실제 브라우저로 전부 돌려본 결과

수정이 진짜 효과가 있는지 확인하려고, 실제 서버를 띄우고 브라우저 자동 테스트 전체를 돌렸습니다. 처음 완주 결과는 375개 통과 / 63개 실패였는데, 63개 실패를 하나하나 추적한 결과 제가 고친 부분에서 나온 실패는 0건이었고, 전부 예전부터 있던 다른 원인들이었습니다. 이것들도 이어서 정리했습니다.

실패 유형 쉬운 설명 조치 상태
브라우저 언어 문제 (약 15건) 비로그인 화면 테스트들이 영어 브라우저로 열려 한국어 글자를 못 찾음 — 2-3의 비밀번호 재설정과 같은 원인이 여러 곳에 있었던 것 해당 테스트들을 모두 한국어로 고정 통과 확인
테스트 데이터 부족 (약 10건) "이런 데이터가 이미 있다"고 가정하는 테스트들인데 개발용 DB에 그 데이터가 없었음 (첨삭 결과 견본, 약점 추천 목록 등) 재사용 가능한 데이터 심기 도구 (scripts/seed-e2e-audit-fixtures.mjs)를 만들어 실제 개발 DB에 견본 데이터를 넣음 통과 확인

환경 전제 (1건) "기관 소속 계정"이 미리 준비된 환경에서만 돌 수 있는 시나리오. 지금 환경에서 억지로 만들면 다른 테스트 전체가 깨짐 전제가 안 갖춰진 환경에서는 실패 대신 건너뜀(skip)으로 표시되게 정리 건너뜀 처리

4. 초기에 "제품 버그"로 의심했다가 재검증으로 바로잡은 건

결론: 제품 문제가 아니었습니다. 로그인 → 화면 이동 흐름은 정상 작동합니다.

자동 테스트를 고치던 중, "로그인 직후 동의 안 한 사용자가 대시보드에 잠깐 들어간다"고 초기에 의심했습니다. 그러나 깨끗한 조건(부가 조건 없는 평범한 로그인)으로 다시 재현해 보니, 동의 안 한 새 사용자는 로그인 직후 곧바로 동의 화면 (/auth/consent)으로 이동했습니다. 필수 동의 확인 장치는 정상 작동합니다.

초기에 "대시보드가 보였다"고 본 것은 측정 착오였습니다. 로그인 성공 시 주소창이 순간적으로 /dashboard로 바뀐 직후 서버가 동의 화면으로 되돌리는데, 그 되돌림이 완료되기 전의 찰나를 읽었던 것입니다(첫 프로브는 대기 없이 즉시 읽었고, 1.5초 기다린 재검증에서는 정상적으로 동의 화면이 나왔습니다).

이 되돌림 타이밍(약 1초) 때문에 자동 테스트의 로그인 보조 코드가 순간의 /dashboard를 보고 동의 처리를 건너뛴 것이, institution 화면 테스트가 실패하던 진짜 원인이었습니다. 그래서 테스트를 "전체 새로고침으로 목적지를 다시 확인"하도록 튼튼하게 고쳐 해결했고, 이 수정은 그대로 유효합니다. 남는 것은 제품 버그가 아니라, 원한다면 비밀번호 로그인도 소셜 로그인처럼 서버 경유로 보내 되돌림이 화면에 보이기 전에 처리하는 선택적 UX 다듬기 정도입니다.

5. 아직 남은 것 (일부러 남긴 3건)

아래 3건은 "테스트가 낡은 건지, 화면이 잘못된 건지"를 디자인/제품 기준으로 결정한 뒤 고쳐야 해서 무단으로 바꾸지 않았습니다. 결정만 내려주시면 바로 진행할 수 있습니다.

항목 결정할 내용
작업 화면 폭 불일치 한 작업 화면이 다른 화면들과 다른 폭을 씁니다. 일부러 넓게 만든 것인지, 실수인지 디자인 기준 확인이 필요합니다.
구독 관리 화면의 제목 없음 "준비 중" 안내만 있는 이 화면에 화면 제목(heading)을 넣을지, 아니면 테스트에서 이 화면만 예외로 둘지 결정이 필요합니다.
첫 화면 버튼 아이콘의 선 굵기 테스트는 선 굵기 2.25를 기대하는데, 공용 아이콘 부품이 이 값을 쓰지 않습니다. 2.25가 지금도 유효한 디자인 기준인지 확인이 필요합니다.
