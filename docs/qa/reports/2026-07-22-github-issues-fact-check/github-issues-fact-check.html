결론

39건 모두를 현재 버그로 보는 것은 맞지 않습니다. 최초 검수 기준인 origin/main 22eb1413에서는 실제 결함이 12건이었지만, #3·#6·#8·#9·#10·#11·#13 수정이 현재 작업 브랜치와 PR #64에 반영돼 남은 현재 결함은 5건입니다. 7건은 수정 완료, 8건은 기존 해결 확인, 11건은 UX 개선 또는 새 요구사항이며, 나머지 8건은 조건이 부족해 단정할 수 없습니다. Closed #12는 집계에서 제외하지만 저장한 문제와 임시 저장 필터의 회귀 검증을 완료했습니다.

이번 재검수에서는 이전 보고서의 일괄 제외 분류를 전부 폐기했습니다. 지정 QA 계정의 기존 제출물과 피드백을 읽기 전용으로 열어 확인했고, 접근 가능한 과거 피드백은 실제 문구와 카드 분리 결과까지 대조했습니다.

변경하지 않은 것

핵심 인사이트

  • 가장 큰 위험은 AI 자체보다 상태 정의의 불일치였습니다. #8은 사용자 완료와 운영 시도를 분리하도록 수정했지만, #37은 제출 22건이 있어도 구조화 점수 행이 없으면 0건으로 센다. 제출·분석·피드백·복습의 공통 상태 계약을 나머지 화면에도 일관되게 적용해야 합니다.
  • 콘텐츠 품질 결함은 문제 데이터와 화면 표현을 분리해 다뤄야 합니다. #3·#10은 고정 힌트를 제거하고 현재 문제의 안전한 데이터만 표시하도록 수정했고, #11은 유형과 맞지 않는 입력 안내를 제거했다. #13은 canonical 원문을 보존하면서 세 질문만 번호 목록으로 구분했다. #9는 문장부호 후처리가 아니라 전체 피드백 노출 문제로 재판정해 수정했으며, #23·#29의 문장 그룹화·내용 품질 문제는 별도 결함으로 남는다.
  • 오래된 이슈 링크가 검증 가능성을 낮춥니다. #16·#22처럼 과거 제출 URL이 404이고 #31·#32는 제출 ID가 없습니다. 앞으로는 문제 ID, 제출 ID, 화면 언어, 기대 결과, 실제 결과를 필수 템플릿으로 받아야 합니다.
  • Open 상태가 현재 작업 필요를 뜻하지는 않습니다. #7·#15·#16·#20·#21·#22·#28·#41은 최신 main에서 해결됐으므로 근거를 댓글로 남기고 close 후보로 정리할 수 있습니다.
  • 11건은 버그 백로그와 분리해야 합니다. UX·요구사항을 결함과 같은 큐로 운영하면 P1 실제 결함의 우선순위가 흐려집니다. `bug`, `ux`, `content`, `requirement`, `needs-evidence` 라벨을 분리하는 편이 좋습니다.
