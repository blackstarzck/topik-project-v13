v13 사용자 화면 ↔ topik-ai 관리자 페이지 정합성 인벤토리

이 HTML은 v13 사용자 화면에서 실제로 쓰는 데이터베이스 객체와 topik-ai 관리자 페이지의 page-sync 기준 관리 후보를 한눈에 비교하기 위한 보고서입니다. 실제 DB 데이터 입력이나 CRUD 검수는 아직 하지 않았습니다.

기준 앱: v13 사용자 화면 관리자 기준: topik-ai docs/page-sync 범위: 문서/소스 조사 실 DB 검수: 미실행

주의할 영역

회원, 결제, 알림은 개념은 겹치지만 테이블과 책임이 1:1로 같지 않습니다.

관리 방식

사용자 작성물, 피드백, 보관함은 기본적으로 직접 CRUD가 아니라 지원/조회 대상입니다.

2. 상태 의미

상태 뜻
직접 겹침 두 앱에 같은 핵심 개념이 있습니다. 단, 필드명과 테이블명 매핑은 더 필요할 수 있습니다.
부분 겹침 관리자 화면은 있지만 범위가 더 넓거나 더 좁거나 이름이 다릅니다.
예정/후보 topik-ai에는 page-sync 후보가 있지만 v13 사용자 화면에는 아직 구현된 DB 사용이 없습니다.
관리 화면 없음 v13 사용자 화면은 데이터를 쓰지만 topik-ai에서 명확한 관리 화면이 보이지 않습니다.
사용자 소유/지원용 관리자가 직접 CRUD하기보다 조회, 지원, 진단 용도로 다루는 쪽이 안전합니다.
내부 전용 사용자 화면에 직접 보이는 데이터가 아닙니다.

7. 즉시 발견한 점

가장 좋은 첫 slice

topik-ai 문제은행은 v13 쓰기 화면의 problems와 직접 이어집니다. JSON fixture 97개도 있어서 문서 다음 단계의 필드 매핑 대상으로 가장 좋습니다.

1:1로 보면 안 되는 영역

회원, 결제, 알림은 이름은 비슷하지만 v13과 topik-ai의 테이블 후보가 다릅니다. 바로 CRUD 검수로 들어가면 잘못된 표를 기준으로 테스트할 위험이 있습니다.

발견 근거 의미
문제은행이 최우선입니다. v13 쓰기/연습 화면이 problems/problem_assets를 사용하고 topik-ai 문제은행은 service/store/schema/JSON fixture를 갖습니다. 문서 다음 단계에서 가장 작고 명확하게 검수 slice를 만들 수 있습니다.
회원 데이터는 이름부터 다릅니다. v13은 profiles, topik-ai는 users 후보입니다. 필드 매핑과 권한 경계가 먼저 필요합니다.
결제/구독은 부분만 겹칩니다. v13은 subscription_plans, subscriptions, payment_history이고 topik-ai는 commerce_payments, commerce_refunds, 상품/패키지 후보입니다. Commerce가 곧 v13 billing을 관리한다고 보면 안 됩니다.
알림은 관리자 캠페인과 사용자 설정을 분리해야 합니다. v13은 개인 설정/로그, topik-ai는 템플릿/대상 그룹/발송 이력입니다. 같은 알림이라는 이유로 한 테이블로 합치면 안 됩니다.
v13에는 사용자 소유 데이터가 많습니다. draft, submission, feedback, library, report, export 등이 사용자 화면에 구현되어 있습니다. 관리자 CRUD가 아니라 지원/조회/진단 화면으로 설계하는 편이 안전합니다.
topik-ai의 planned surface도 많습니다. 공지, FAQ, 이벤트, 포인트, 단어장, 배지, 미션 등은 page-sync 후보지만 v13 backing table 확인이 안 됐습니다. 현재 v13 관리 누락이라고 단정하지 않습니다.
