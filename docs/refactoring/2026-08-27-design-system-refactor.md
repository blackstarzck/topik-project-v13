# 2026-08-27 디자인 시스템 리팩토링: 승인 계획과 결과

## 목적과 범위

사용자가 보기에 같은 기능과 학습 흐름을 유지하면서, 화면 구성 요소·스타일·디자인 토큰의 책임을 정리한다. 이후 테마를 바꾸거나 화면을 확장할 때 같은 색·간격·글꼴 값을 여러 곳에서 고치지 않도록 하는 것이 목표다.

이번 작업은 사용자용 앱에 한정한다. 관리자 기능, 원격 데이터베이스 구조 변경, 운영 데이터 직접 변경은 범위에 포함하지 않는다.

## 기준 문서

- 제품 동작과 범위는 `docs/prd.md`를 따른다.
- 데이터 구조와 권한은 `supabase/migrations/` 및 `docs/supabase/`를 따른다.
- 화면 원칙은 `DESIGN.md`, 검증 원칙은 `TESTING.md`를 따른다.
- 이 문서는 이번 리팩토링의 최종 승인 계획과 결과만 보관한다. 작업 중 임시 메모와 증거는 저장소에 보관하지 않는다.

## 단계별 승인 계획과 결과

| 단계 | 승인한 작업 | 결과 |
| --- | --- | --- |
| Phase 0 | 기존 제품·데이터 계약을 확인하고, 원격 데이터베이스를 직접 바꾸지 않는 경계를 정한다. | 완료. 일반 사용자 흐름의 저장 검증만 허용하고, 운영 데이터베이스 직접 작업은 수행하지 않는다. |
| Phase 1 | 전역 스타일을 기반 스타일과 화면별 스타일로 분리하고, 기존 화면의 시각적 의미를 디자인 토큰으로 옮긴다. | 완료. 공통 색·간격·글꼴·그림자·반경을 토큰으로 연결했다. |
| Phase 2 | 반복되는 화면 요소를 재사용 가능한 구성 요소와 범위가 분명한 스타일로 정리한다. | 완료. 공통 모달·카드·알림·작성 화면의 중복 스타일을 정리했다. |
| Phase 3 | 대시보드, 보관함, 문제 풀이, 작문 흐름에 정리한 구성 요소와 토큰을 적용한다. | 완료. 이동·초안 이어쓰기·자동 저장·제출 전 확인 등 기존 학습 흐름을 유지한다. |
| Phase 4 | 스타일 규칙을 기준선으로 고정하고, 새 위반 없이 전환할 수 있도록 사전 승인 기준을 적용한다. | 완료. 전역 CSS 전환 범위만 허용하고, 임의의 새 인라인 스타일·색상·스타일 규칙은 차단한다. |
| Phase 5 | 기능·화면·저장 결과를 최종 확인하고, 병합 뒤 작업 공간을 정리한다. | 진행 중. 최종 PR의 전체 자동 검사와 병합 뒤 정리까지 완료 조건으로 둔다. |

## 스타일 운영 원칙

- 디자인 토큰이 색상, 글꼴, 간격, 반경, 그림자의 기준이다. 화면 코드는 토큰을 사용한다.
- 공통 화면 요소는 재사용 가능한 구성 요소와 범위가 정해진 스타일을 우선한다.
- Tailwind는 배치와 제한된 보조 스타일에만 사용한다. 브랜드 색·글꼴·그림자·반경처럼 테마 영향을 받는 값은 토큰 또는 컴포넌트 스타일로 관리한다.
- Ant Design은 기존 테마와 구성 요소 체계를 우선 사용한다. 같은 역할의 별도 스타일 체계를 새로 만들지 않는다.
- 예외가 꼭 필요한 경우에는 이유, 만료 조건, 회귀 검증을 함께 기록하고 새 예외는 자동 검사에서 드러나야 한다.

## 완료 검수 기준

1. 관련 단위·통합 검사가 통과하고, 타입·정적 분석·빌드가 최종 PR에서 통과한다.
2. 실제 브라우저에서 데스크톱과 모바일 화면을 확인한다.
3. 로그인된 사용자 흐름에서 이동·입력·저장·새로고침 후 재표시를 확인해, 단순 응답 코드가 아닌 실제 기능 결과를 검수한다.
4. 기준선 전환은 정확히 승인된 전역 스타일 범위에서만 허용한다.
5. 최종 PR 병합 뒤 관리 작업 공간과 실행 중인 개발 서버를 정리한다.

## 남은 위험과 후속 원칙

- 테마 전환을 실제 사용자에게 열 때는 라이트·다크 테마 각각에 대해 화면과 접근성 검수를 별도로 수행한다.
- 인증 계정이 유효하지 않으면 저장 검증을 성공으로 처리하지 않는다. 유효한 테스트 계정 또는 승인된 E2E 계정으로 다시 검증한다.
- 다음 정기 리팩토링도 이 문서와 같은 형식으로 최종 승인 계획과 결과만 `docs/refactoring/`에 추가한다.
