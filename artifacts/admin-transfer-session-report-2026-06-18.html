이번 세션의 핵심은 v13은 사용자 화면으로 유지하고, 관리자 전용 데이터·RPC·알림 발송 워커는 topik-ai 관리자 앱이 소유하도록 경계와 검증 장치를 만드는 것이었습니다.

v13 = user-facing app topik-ai = admin app SOT 직접 수정 최소화 production handoff는 아직 남음
완료 로컬 경계 분석과 검사 장치
보류 Vercel production 연결과 실증 evidence
유지 v13 사용자 알림/결제/동의/프로필 범위
이관 관리자 객체와 email worker 소유권

1. 요청사항별 실행 상태

요청사항 실행 상태 설명
v13과 topik-ai의 역할 구분 적용됨 v13은 사용자 화면, topik-ai는 관리자 화면이라는 기준으로 DB 객체, RPC, 워커 소유권을 재분류했습니다.
각 프로젝트의 SOT 문서 확인 적용됨 topik-ai의 SOT checklist script가 v13/topik-ai 필수 문서를 출력하고 누락을 실패로 처리하도록 만들었습니다.
phase 단위 작업 적용됨 Phase 0 local boundary, Phase 1 production handoff gate, v13 transition route retirement gate로 분리했습니다.
테이블/객체 이관 판단 적용됨 topik-ai 소유, v13 유지, shared owner-read 범위를 구분하고 proposal과 checker에 반영했습니다.
v13/topik-ai 교차 검증 적용됨 npm run harness:admin-transfer:local 하나로 양쪽 로컬 경계 검증을 실행하게 했습니다.
topik-ai 관리자 계정 기반 검증 로컬 조건 확인 .env.local의 E2E_ADMIN_EMAIL, E2E_ADMIN_PASSWORD 존재를 검사합니다. 값은 출력하지 않습니다.
production 최종 이관 완료 미완료 Vercel project link, production runtime env, 실제 production evidence가 아직 없습니다.

2. 어디까지 적용됐는가

Phase 0 · 로컬 경계 확정

적용됨

v13 코드와 테스트에서 제거되었거나 topik-ai가 소유해야 하는 관리자 객체를 직접 참조하지 않는지 검사했습니다. 동시에 v13에 남아야 하는 사용자 객체는 계속 허용했습니다.

  • v13 user-facing/shared: profiles, notification_settings, user_notifications, notification_delivery_attempts owner-read, 결제/동의 관련 객체
  • topik-ai admin-owned: 관리자 RPC, 알림 발송/이력, 운영/커뮤니티/커머스/시스템 관리자 객체
  • v13 historical admin island: org/assignment/admin problem RPC 계열은 현재 v13 사용자 앱 범위가 아닌 것으로 정리

Phase 1 · topik-ai 관리자 소유권 강화

적용됨

topik-ai에서 관리자 소유 객체와 migration directory를 검증하는 script를 추가했습니다. v13 historical migration에 남은 과거 흔적은 warning으로 보고하고, 현재 소유권 판단은 topik-ai admin migration과 v13 제거 migration을 함께 봅니다.

Phase 2 · v13 SOT 직접 수정 대신 변경 제안

적용됨

v13의 active SOT는 직접 고치지 않았습니다. 대신 docs/sot-change-proposals/2026-06-18-admin-ownership-transfer-to-topik-ai.md에 어떤 문서를 어떤 방향으로 정리해야 하는지 제안으로 남겼습니다.

Phase 3 · 알림 email worker 이관 준비

production 검증 대기

topik-ai가 server-only email worker를 소유하도록 runbook, smoke check, evidence check를 준비했습니다. 다만 실제 production Vercel 연결과 runtime env가 없으므로 v13 transition route는 아직 제거하지 않았습니다.

5. 아직 남은 일

중요: 현재 작업은 로컬 경계와 검증 장치까지는 정리됐지만, production handoff까지 끝난 상태는 아닙니다.
  • topik-ai를 실제 Vercel project에 연결해야 합니다. 현재 .vercel/project.json이 없습니다.
  • production runtime env가 필요합니다: NOTIFICATION_WORKER_SECRET, CRON_SECRET, RESEND_FROM, SITE_URL.
  • operator smoke용 TOPIK_AI_PRODUCTION_URL이 필요합니다.
  • 실제 production smoke 결과를 docs/runbooks/notification-worker-production-evidence.md에 기록해야 합니다.
  • 그 evidence에서 topik-ai admin history와 v13 owner-read history가 모두 확인되어야 합니다.
  • 그 후에야 v13 transition route 제거 여부를 결정할 수 있습니다.

6. 왜 이 방향이 맞는가

Supabase 공식 문서는 service role key가 RLS를 우회할 수 있으므로 브라우저나 사용자에게 노출하지 말아야 한다고 설명합니다. 따라서 email worker처럼 service-role/provider secret을 쓰는 기능은 v13 사용자 앱이 아니라 topik-ai 서버 런타임에 두는 것이 안전합니다.

Vercel 공식 문서는 environment variable을 소스 코드 밖에서 관리하고, 민감한 환경 변수는 production/preview 환경에서 값을 읽을 수 없게 보호할 수 있다고 설명합니다. 그래서 이번 작업은 secret 값을 코드나 문서에 남기지 않고, 변수명과 pass/fail evidence만 기록하도록 설계했습니다.

  • Supabase Row Level Security docs
  • Vercel Environment Variables docs
  • Vercel Sensitive Environment Variables docs

7. 한 줄 결론

v13에서 관리자 책임을 topik-ai로 옮기기 위한 로컬 경계, SOT checklist, 교차 검증, production gate는 구축되었습니다. 다만 실제 production worker handoff는 Vercel 연결과 운영 evidence가 있어야 완료로 처리할 수 있습니다.
