비개발자용 설명서 · IA 구현 검수 워크플로우

34개 IA를 증거로 검수하고 최종 PASS를 스크립트로 막는 절차입니다

기준 문서의 실행 계획을 바탕으로, 문서 영수증부터 브라우저 증거, 보안 증거, 에이전트 검수, AI/사람 UX 판단, 최종 검증까지 한눈에 보이게 정리했습니다.

한 줄 결론

이 절차의 목표는 “현재 IA 화면, 팝업, 상태, 서버 경로가 실제로 쓸 수 있는 수준인지”를 증명하는 것입니다. 페이지가 열린다는 사실만으로는 부족합니다. 문서 기준, 화면 증거, 팝업 상태, 로그인과 권한, 뒤로가기와 직접 URL, 사람 판단이 필요한 UX까지 확인합니다. 마지막 PASS는 사람이 손으로 쓰는 값이 아니라 스크립트가 계산하고 검증하는 값입니다.

비유하면 건물 완공 검사입니다

문이 열리는지만 보면 부족합니다. 안내판, 비상구, 조명, 동선, 직원 전용 구역까지 봐야 “사용 가능”이라고 말할 수 있습니다. 이 문서는 그 검사를 빠짐없이 반복하는 순서표입니다.

이번 변경의 핵심

핵심은 “실행 단위가 분리된, 증거 기반 검수 흐름”입니다. 먼저 34개 IA 명단과 문서 영수증을 만들고, 브라우저/팝업/보안 증거를 JSON으로 남깁니다. 그다음 증거 묶음을 고정한 뒤에만 IA 묶음 에이전트를 투입합니다. 에이전트는 PASS를 추천할 수 있지만 최종 PASS를 확정할 수는 없습니다.

Phase 5에서는 AI가 먼저 UX 위험을 정리하고, 사람은 문구 자연스러움, 모바일 체감, 신뢰감, 정책성 문구처럼 판단이 필요한 부분을 확인합니다. 마지막 Phase 6에서 결과를 합치고 검증 스크립트가 빠진 증거, 섞인 실행 ID, 낡은 결과, AI가 대신 쓴 사람 확인을 막습니다.

34 현재 IA 항목

docs/IA/README.md 기준의 현재 검수 대상입니다.

JSON 최종 판정의 원본 증거

문서, 화면, 팝업, 보안 결과는 스크립트가 읽을 수 있어야 합니다.

6개 기본 IA 묶음

공개/인증, 온보딩·대시보드, 작성, 피드백, 보관함/설정, 관리자 6개로 나눠 봅니다.

검증 PASS 차단 장치

증거 없는 PASS, 낡은 결과, AI가 대신 쓴 사람 확인을 마지막에 막습니다.

현재 출발점

실행 계획 문서가 잡고 있는 현재 상태입니다. 이 상태를 먼저 확인하고 나서 검수 자동화를 돌립니다.

IA는 34개

docs/IA/README.md는 34개 IA 폴더를 기준으로 봅니다. sitemap의 32개 표현은 구현 실패가 아니라 문서 틈으로 표시합니다.

E2E는 아직 27개 중심

현재 E2E 매트릭스는 32-route 시절 흔적이 있고, 보이는 IA route 중 일부가 빠져 있습니다.

빠진 route 후보

C-03, D-M1, D-M2, D-M3, F-M1, X-11, X-12를 추가 확인해야 합니다.

인증 준비 파일 틈

/auth/sign-out 서버 처리 경로와 tests/e2e/auth-state/{role}.json 준비 상태를 확인해야 합니다.

워크플로우 다이어그램

핵심 순서는 “문서 기준 잡기 → 자동 증거 만들기 → 증거 묶음 고정 → 에이전트 검수 → AI/사람 UX 판단 → 최종 병합과 검증”입니다. 옆에는 늘 흐름 감시관이 함께 돌면서 단계 전환마다 “증거 없는 PASS”나 “이른 BLOCKED”를 막습니다.

Phase 0 기준 문서와 실행 폴더 준비

docs/sitemap.md, docs/IA/README.md, user flow, PRD, spec 순서로 기준을 잡고 reports/ia-verification/runs/<runId>를 만듭니다.

Phase 0.5 문서 영수증 Gate

각 IA마다 읽은 문서, 뽑은 요구사항, 충돌 여부를 doc-receipts.json에 남깁니다. 영수증이 없으면 PASS는 막힙니다.

Phase 1 IA 명단과 분담 계획 만들기

ia-manifest.json, source-map-results.json, agent-dispatch-plan.json을 준비합니다. 이때는 아직 에이전트를 투입하지 않습니다.

Phase 2 브라우저 화면 증거

페이지 route를 실제 브라우저에서 열고 모바일, 태블릿, 데스크톱, 빈 화면, 로딩, 에러 상태를 남깁니다.

Phase 3 팝업과 화면 안 상태 증거

모달, 토스트, 자동저장, 제출 확인, 내보내기, AI 분석 로딩처럼 host route 안에서 뜨는 상태를 확인합니다.

Phase 4 보안과 이동 증거

로그인 전후, role, owner id, 직접 URL, 새로고침, 로그아웃 뒤로가기, raw error 노출을 확인합니다.

Gate 증거 묶음이 고정됐나?

runId, sourceCommit, dirtyState, evidenceBundleId가 맞는지 봅니다. 바뀐 입력은 낡은 증거로 처리합니다.

Dispatch IA 묶음 에이전트 투입

필수 증거가 있거나 명확히 BLOCKED로 표시된 뒤에만 작업 지시서를 만들고 shard별 검수를 맡깁니다.

Phase 5 AI-first UX와 사람 확인

AI가 모든 IA의 UX 위험 카드를 만들고, 사람은 판단이 필요한 문구, 신뢰감, 모바일, 정책 질문을 확인합니다.

Phase 6 결과 병합

pnpm test:ia:merge로 모든 JSON 결과를 합쳐 ia-implementation-audit.json과 Markdown 리포트를 만듭니다.

Final Gate 최종 검증

pnpm test:ia:validate가 증거 없는 PASS, 사람 확인 누락, 에이전트 결과 누락, 섞인 실행 ID를 막습니다.

Done or Re-run 최종 판정 또는 재실행

상류 문서나 구현이 바뀌면 Phase 0.5~4를 다시 돌리고, 바뀐 IA는 Phase 5~6도 다시 돌립니다. 영향 받지 않은 IA만 옛 결과를 재사용할 수 있는데, 이때 carryover-map.json에 “어느 실행에서 가져왔는지”를 남기지 않으면 통과되지 않습니다.

빠진 증거가 있으면 “대충 PASS”가 아니라 BLOCKED, PARTIAL, FAIL, DOC-GAP, DEFERRED 중 하나로 남기고 다시 실행합니다.
흐름 감시관(audit flow monitor)은 위 모든 단계와 나란히 흐르는 별도 트랙입니다. 단계가 넘어가기 전마다 “이 단계에 나와야 할 증거가 빠졌는지”, “이른 PASS/BLOCKED는 없는지”를 audit-flow-monitor.json에 기록합니다. 감시관은 검수원 자리를 차지하지 않습니다. 단, 동시에 IA 묶음 검수원과 같이 돌면 한 번에 돌리는 자식 에이전트가 6명을 넘지 않도록 검수원은 5명으로 줄입니다.
상류 문서나 코드가 바뀌면 영향받은 IA만 다시 돌립니다. 이때 옛 Phase 5 결과와 새 상류 증거를 섞지 못하도록 carryover-map.json에 “어떤 IA를 어느 실행에서 재사용했는지”를 남기고, 한 IA의 증거 묶음은 그 안에서 끝까지 일관되어야 합니다.

스크립트는 감독관 역할을 합니다

비유하면, 사람이 쓴 검사 메모 옆에서 감독관이 도장을 찍는 구조입니다. 도장 조건이 빠지면 최종 통과가 되지 않습니다.

문서 영수증 검사

문서를 읽었다면 어떤 문서에서 어떤 요구사항을 뽑았는지 남겨야 합니다.

증거 파일 검사

브라우저, 팝업, 권한, 뒤로가기 결과가 JSON으로 남아 있는지 봅니다.

최종 PASS 검사

증거가 빠졌는데 PASS라고 적힌 항목을 마지막에 막습니다.

에이전트는 조별 검사원처럼 움직입니다

34개 IA를 한 에이전트가 전부 기억해서 보는 방식은 놓치기 쉽습니다. 그래서 공개/인증, 온보딩, 작성, 피드백, 보관함/설정, 관리자/보안처럼 묶음을 나눕니다. 단, 브라우저, 팝업, 보안 증거가 준비되기 전에는 에이전트를 투입하지 않습니다. 각 에이전트는 자기 묶음만 깊게 보고, 최종 판정은 진행 관리자와 스크립트가 합칩니다.

진행 관리자

누가 어떤 IA 묶음을 볼지 정하고, 결과 패킷을 받아 출처 기록과 충돌을 남깁니다.

IA 묶음 에이전트

담당 묶음의 문서, 화면 증거, UX 위험을 보고 추천 라벨과 JSON 결과를 냅니다.

최종 검증

에이전트 추천은 입력일 뿐입니다. 결과 패킷, 해시, 실행 출처, 기준 코드가 빠지면 PASS가 막힙니다.

단계별로 쉽게 보기

Phase 0

먼저 기준표를 정합니다

docs/sitemap.md, docs/IA/README.md, docs/flow/user-flow.md를 기준으로 삼습니다. 이때 pnpm test가 실패해도 무조건 막지 않고 “테스트 거리가 없어서”인지, “실제 코드가 깨졌는지”, “환경이 빠졌는지”를 네 가지 사유로 나눠 기록합니다. 진짜 코드 회귀(fail-product-regression)만 단계 진입을 막습니다.

Phase 0.5

문서 읽기 영수증을 남깁니다

각 IA마다 읽은 문서, 뽑은 요구사항, 문서 충돌 여부를 doc-receipts.json에 남깁니다. 영수증 뼈대는 build-doc-receipts.mjs가 IA 폴더·사이트맵·user-flow·PRD를 훑어 자동으로 만들고, 사람이 “요구사항” 칸을 채웁니다. verify-doc-receipts.mjs가 비어 있거나 description.md가 빠진 영수증을 막습니다. 이 영수증이 없으면 최종 통과가 안 됩니다.

Phase 1

검수 대상 명단을 만듭니다

34개 IA가 전부 있는지, 실제 코드에 맞는 주소가 있는지 확인합니다. 결과는 ia-manifest.json과 source-map-results.json으로 남깁니다.

Phase 1 dispatch plan

IA를 묶음으로 나눌 계획만 먼저 만듭니다

agent-dispatch-plan.json으로 공개/인증, 온보딩·대시보드, 작성, 피드백, 보관함/설정, 관리자 6개 묶음을 정합니다. 이 단계는 분담표 준비이고, 실제 에이전트 투입은 증거 묶음이 고정된 뒤에 합니다. dispatch 검사는 화면 sync 검사(static)가 끝나지 않아도 돌릴 수 있습니다.

Phase 2

브라우저로 화면을 엽니다

모바일, 태블릿, 데스크톱 크기에서 제목과 주요 버튼이 보이는지 봅니다. 빈 화면, 에러, 로딩, 입력 안내 같은 상태도 AI가 볼 증거로 남깁니다. 권한 파일(student, content_admin, org_admin, platform_admin)이 부분만 준비되면 누락된 권한의 화면만 막고, 준비된 권한은 그대로 검사를 진행합니다.

Phase 3

팝업과 대기 상태를 봅니다

제출 확인, AI 분석 로딩, 자동저장 경고, PDF 내보내기 같은 화면 안의 화면을 확인합니다. 열기 전, 열린 뒤, 닫은 뒤 상태도 AI가 볼 증거로 남깁니다.

Phase 4

외부 접근과 권한을 봅니다

직접 URL, 다른 사람의 결과 id, 관리자 주소, 로그아웃 뒤로가기 같은 위험한 진입을 확인합니다. 사용자가 어디에 있는지, 어디로 돌아가면 되는지 안내 문구도 증거로 남깁니다.

Evidence freeze

증거 묶음을 고정합니다

이 단계가 “묶음 도장”을 찍습니다. sourceCommit(코드 시점)과 dirtyState(작업물이 깨끗한지 더러운지)는 자동으로, evidenceBundleId는 Phase 0.5~4 증거 줄의 해시로 한 번에 계산되어 Phase 5·6 줄에 똑같이 박힙니다. id 계산식이 미리 못 박혀 있어 병합기와 검증기가 서로 다르게 계산해서 거짓 통과·거짓 차단이 생기는 일을 막습니다.

Dispatch

필요할 때만 IA 묶음 에이전트를 투입합니다

필수 브라우저, 팝업, 보안 증거가 있거나 명확히 BLOCKED로 표시된 뒤에 작업 지시서를 보냅니다. 단일 세션으로 처리할 때도 같은 JSON 형식을 채웁니다.

Phase 5

AI가 먼저 UX를 보고, 사람이 최종 확인합니다

AI는 앞 단계에서 모은 JSON 증거와 에이전트 결과 패킷을 읽고 모든 IA의 리뷰 카드를 만듭니다. 사람은 AI가 제시한 질문을 중심으로 최종 UX 판단을 합니다.

  • 첫 제목만 봐도 현재 위치를 아는가?
  • 뒤로가기와 직접 URL 진입이 자연스러운가?
  • AI 추천과 피드백의 근거와 한계가 보이는가?
  • 에러가 “무슨 일 / 왜 문제 / 고치는 법”을 알려주는가?
  • 모바일, 키보드, 모달 포커스가 안전한가?
Phase 6

최종 리포트를 만들고 검증합니다

pnpm test:ia:merge로 결과를 합치고 pnpm test:ia:validate로 최종 PASS가 가능한지 검사합니다. Markdown 설명은 JSON에 적힌 막힌 이유를 덮어쓸 수 없습니다.

결과표는 신호등처럼 봅니다

PASS

문서, 화면, 흐름, 증거가 맞습니다.

PARTIAL

큰 줄기는 되지만 증거나 세부 UX가 부족합니다.

FAIL

사용자 혼란, 접근성 문제, 보안/정책 위험이 있습니다.

DEFERRED

문서상 나중 범위라 지금 실패로 보지 않습니다.

DOC-GAP

문서가 결정을 안 해서 판단할 수 없습니다.

BLOCKED

계정, 데이터, 환경이 없어 검수할 수 없습니다.

여러 에이전트가 어떻게 나눠 보나요?

이 부분은 한 명의 리뷰어 목록이 아니라, 검수 공장 라인처럼 보면 됩니다. 진행 관리자가 IA 묶음을 나누고, 여러 에이전트가 동시에 보고, 마지막에는 스크립트가 증거를 대조합니다.

1. 진행 관리자

IA를 묶음으로 나누고, 작업 지시서와 최종 병합을 책임집니다.

2. 기획 검수자

PRD, 사이트맵, IA 폴더, user-flow가 서로 맞는지 먼저 보고 충돌을 알립니다.

3. 자동화 담당

스크립트와 테스트로 문서, 화면, 보안 증거가 빠졌는지 확인합니다.

4. 흐름 감시관

단계 전환마다 “나와야 할 증거가 있는지”, “이른 PASS/BLOCKED는 없는지”를 별도 트랙에서 적습니다. 검수원 자리를 차지하지 않습니다.

5. IA 묶음 에이전트 1~6

공개/인증, 온보딩·대시보드, 작성, 피드백, 보관함/설정, 관리자 6개 묶음을 동시에 봅니다.

6. 재검토 에이전트

서로 말이 다르거나 위험한 IA를 한 개씩 다시 확인합니다.

7. AI UX 종합 리뷰어

묶음 에이전트 결과와 화면 증거를 합쳐 UX 위험과 질문을 정리합니다.

8. 사람 UX 리뷰어

문구, 화면 이해도, 모바일 체감, 신뢰감처럼 사람 판단이 필요한 부분을 봅니다.

9. 보안/데이터 에이전트

권한, 세션, 다른 사람 데이터 노출, 관리자 접근을 깊게 봅니다.

10. 운영/정책 에이전트

결제, 알림, 개인정보, 오류 복구 문구가 문서와 맞는지 봅니다.

11. 최종 검증 스크립트

에이전트 추천이 아니라 JSON 증거 기준으로 최종 PASS를 막거나 허용합니다.

최종 산출물

reports/ia-verification/runs/<runId>

한 번의 검수 실행이 쓰는 독립 폴더입니다. 진행 중인 실행은 latest에 직접 쓰지 않습니다.

reports/ia-verification/latest

test:ia:merge와 test:ia:validate가 통과한 뒤에만 갱신하는 최신 결과 포인터입니다.

doc-receipts.json

각 IA마다 어떤 문서를 읽고 어떤 요구사항을 뽑았는지 남긴 영수증입니다. 뼈대는 build-doc-receipts.mjs가 자동으로 만듭니다.

build-doc-receipts.mjs

IA 폴더·사이트맵·user-flow·PRD를 훑어 영수증 뼈대를 자동 생성하는 스크립트입니다. 사람이 비어 있는 “요구사항” 칸만 채우게 만듭니다.

audit-flow-monitor.json

흐름 감시관이 단계 전환 때마다 “나와야 할 증거가 있는지”, “이른 PASS/BLOCKED는 없는지”를 기록하는 파일입니다. 최종 검증 스크립트가 이 파일도 함께 봅니다.

carryover-map.json

변경 안 된 IA의 결과를 옛 실행에서 가져올 때 “어느 실행에서, 어느 증거 묶음 id로, 왜” 가져왔는지를 남기는 파일입니다. 이 기록이 없으면 옛/새 증거 혼용으로 보고 통과를 막습니다.

ia-manifest.json

검수할 34개 IA 항목을 스크립트가 읽을 수 있게 정리한 명단입니다.

source-map-results.json

문서의 화면과 실제 코드 위치가 연결되는지 본 결과입니다.

static-results.json

문서와 코드가 서로 맞는지 본 결과입니다.

browser-results.json

브라우저로 실제 화면을 열어 본 결과입니다.

hosted-surface-results.json

팝업, 로딩, 자동저장 경고처럼 화면 안에서 뜨는 상태를 본 결과입니다.

security-navigation-results.json

로그인, 권한, 뒤로가기, 직접 URL 접근을 본 결과입니다.

agent-dispatch-plan.json

어떤 IA 묶음을 어떤 에이전트가 볼지 정리한 분담표입니다.

agent-packets/tasks/*.md

에이전트에게 주는 작업 지시서입니다. 읽을 문서, 볼 증거, 건드리면 안 되는 범위를 적습니다.

agent-packets/results/*.md

에이전트가 돌려주는 결과 보고서입니다. 추천 라벨, 부족한 증거, 질문을 남깁니다.

agent-packets/results/*.json

에이전트 결과를 최종 병합기가 읽을 수 있게 만든 IA별 기계 판독 결과입니다.

agent-integration-results.json

진행 관리자가 에이전트 결과를 받아들였는지, 되돌렸는지, 재검토로 보냈는지 남긴 파일입니다.

ai-ux-review.json / .md

AI가 먼저 본 UX 준비도 카드입니다. JSON이 원본 증거이고 Markdown은 사람이 읽기 쉬운 설명입니다.

manual-review.json / .md

사람이 최종 확인한 UX 판단 기록입니다.

ia-implementation-audit.json / .md

34개 IA의 최종 성적표입니다. AI 판단, AI 확신도, 사람 확인, 최종 UX 결과를 따로 남깁니다.

merge-ia-audit-results.mjs

여러 증거 파일을 모아 최종 성적표를 만드는 스크립트입니다.

validate-ia-audit-report.mjs

증거 없이 PASS가 적힌 항목을 마지막에 막는 스크립트입니다.

최종 성적표는 증거 칸을 분리합니다

기획/문서 결과

IA code, screen name, route, audience, 문서 영수증과 문서 충돌을 따로 둡니다.

AI UX 결과

AI 판단, AI 확신도, AI가 사람에게 넘긴 질문을 분리합니다.

사람 확인

사람 확인이 필요한 항목과 실제 확인 여부를 JSON으로 남깁니다.

개발/QA 증거

정적 검사, 브라우저, 팝업, 서버 처리 경로, 검수 증거를 분리합니다.

보안/정책 결과

권한, 다른 사람 데이터 접근, 세션, 결제/알림 나중 범위를 따로 둡니다.

최종 라벨

agent recommendation과 coordinator decision을 기록하되, final label은 병합 스크립트가 계산합니다.

가장 중요한 안전장치

  • 페이지가 열린다고 곧바로 통과가 아닙니다.
  • 문서 영수증이 없으면 통과가 아닙니다.
  • AI가 봤다고 사람 판단이 사라지는 것은 아닙니다.
  • 에이전트가 PASS라고 추천해도 최종 PASS가 아닙니다.
  • 브라우저, 팝업, 보안 증거가 준비되기 전에는 IA 묶음 에이전트를 투입하지 않습니다.
  • 에이전트 결과 보고서가 없으면 해당 IA는 막힌 상태로 둡니다.
  • 에이전트 결과에는 실행 출처, 기준 코드, 해시, 진행 관리자 결정이 남아야 합니다.
  • 스크린샷이나 브라우저 증거가 없으면 통과로 두지 않습니다.
  • runId, sourceCommit, evidenceBundleId가 섞이면 PASS가 막힙니다.
  • 진행 중인 실행은 latest에 직접 쓰지 않습니다.
  • 최종 PASS는 손으로 적는 값이 아니라 스크립트가 계산하고 검증하는 값입니다.
  • Markdown 설명과 JSON 결과가 다르면 JSON과 검증 스크립트를 우선합니다.
  • 모달은 부품 파일만 보지 않고 실제 열리는 화면에서 확인합니다.
  • 결제와 알림처럼 아직 미룬 기능은 실제 동작하는 것처럼 말하면 안 됩니다.
  • 흐름 감시관이 매 단계 전환을 확인하지 않으면 다음 단계로 넘어갈 수 없습니다.
  • evidenceBundleId는 Phase 0.5~4 증거 묶음의 해시로 자동 계산되어 Phase 5·6 줄에 박힙니다. 사람이 임의로 못 적습니다.
  • pnpm test가 실패해도 무조건 막지 않습니다. “테스트 거리 없음·미구현·환경 부재”는 사유 기록 후 진행, “진짜 코드 회귀”만 단계를 막습니다.
  • 변경 없는 IA를 옛 실행에서 가져올 때는 carryover-map.json에 출처를 남겨야 합니다.
  • 권한 파일(student / 관리자 3종)이 부분만 준비됐을 때는 누락된 권한 시나리오만 막고 나머지는 진행합니다.

용어집

IA

화면 목록과 화면 안 구조입니다.

Manifest

검수할 34개 항목을 한 줄씩 모은 명단입니다.

E2E

사용자처럼 처음부터 끝까지 눌러보는 자동 검사입니다.

Hosted modal

별도 주소가 아니라 다른 화면 위에 뜨는 팝업입니다.

Direct URL

버튼을 누르지 않고 주소창으로 바로 들어오는 경우입니다.

CTA

가장 중요한 행동 버튼입니다. 예: 제출하기, 시작하기.

문서 영수증

어떤 문서를 읽고 어떤 요구사항을 뽑았는지 남긴 기록입니다.

Run ID

이번 검수 실행을 구분하는 이름입니다. 실행마다 독립 폴더를 씁니다.

Evidence bundle

브라우저, 팝업, 보안, 문서 영수증 같은 증거 묶음입니다.

Source commit

증거를 만들 때 기준이 된 코드 시점입니다. 코드가 바뀌면 예전 증거는 낡을 수 있습니다.

IA 묶음

비슷한 화면을 한데 묶어 한 에이전트가 담당하게 만든 작은 검수 단위입니다.

작업 지시서

에이전트에게 “이 문서와 이 증거를 보고, 이 범위만 확인해줘”라고 주는 안내서입니다.

결과 패킷

에이전트가 검수 뒤에 돌려주는 보고서입니다. 추천 라벨과 부족한 증거가 들어갑니다.

출처 기록

결과가 어디서 왔는지 남기는 기록입니다. 에이전트 ID, 해시, 가져온 시점이 포함됩니다.

JSON

스크립트가 읽기 쉬운 정리 파일입니다. 최종 검문소의 기준 자료입니다.

검증 스크립트

빠진 증거나 잘못된 PASS를 자동으로 잡는 검사 프로그램입니다.

흐름 감시관 (audit flow monitor)

코디네이터가 단계를 제대로 넘기고 있는지 옆에서 확인하는 별도 트랙입니다. 검수원 자리는 차지하지 않고, 단계 전환마다 “필요 증거가 모였는지”, “이른 PASS/BLOCKED는 없는지”를 적습니다.

증거 묶음 id

한 실행에서 만든 Phase 0.5~4 증거 줄을 해시로 묶은 id입니다. Phase 5·6의 모든 줄이 같은 id여야 통과됩니다. 사람이 임의로 못 적습니다.

Carry-over

변경 영향 없는 IA의 결과를 옛 실행에서 그대로 가져오는 일입니다. 출처를 carryover-map.json에 남기지 않으면 옛/새 증거 혼용으로 보고 통과를 막습니다.

테스트 실패 4분류

Phase 0에서 pnpm test가 실패할 때 “테스트 거리 없음·미구현 상태·진짜 코드 회귀·환경 부재” 중 어느 것인지를 분류해 기록합니다. 진짜 코드 회귀만 단계를 막습니다.
