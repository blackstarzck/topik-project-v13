실 사용자 검증 중 발견한 production 이슈 + Phase 8.5 fix

사용자분이 실제로 받은 인증 메일을 클릭했을 때 "처리 중 문제가 생겼어요" 화면이 나왔어요. Playwright로 메일 본문까지 들어가서 진단한 결과 두 layer의 이슈를 발견하고 fix 완료.

발견Implicit flow URL fragment 이슈

무슨 일?Supabase가 `/auth/v1/verify` 응답으로 오류 정보(`error_code=otp_expired`)를 URL fragment(`#`)에 박아 보냄. 우리 callback Route Handler는 server-side라 fragment를 못 봄 → 모든 implicit flow 오류가 `reason=unknown`으로 fallback → 사용자는 "처리 중 문제가 생겼어요" generic 메시지만 봄.

왜 문제?PKCE flow(실 SignUpForm)는 정상이지만, 옛 메일이나 implicit flow signup으로 발송된 모든 메일이 정확한 안내를 못 받음. 30일 후 cleanup 사용자 복귀 케이스도 영향.

고친 법?Phase 8.5: `/auth/callback`을 Route Handler에서 Page Component로 변환 + 새 client component `CallbackFragmentFallback`이 useEffect에서 `window.location.hash` 파싱 → 정확한 reason으로 매핑 → `/auth/error?reason=otp_expired` 친절 안내. commit dc17a70.

검증Phase 8.5 fix Playwright로 직접 시각 검증

Before사용자가 옛 메일 클릭 → "처리 중 문제가 생겼어요" (unknown)

After같은 implicit flow fragment → "인증 링크가 만료됐어요" (otp_expired) + "인증 메일 다시 받기" 정확한 CTA

용어집 — 헷갈리는 단어 풀이

auth.users / public.profiles
Supabase가 관리하는 로그인 정보 테이블(auth.users) + 우리 앱이 관리하는 프로필 정보(public.profiles). 같은 id로 묶여 있어서 한쪽 삭제되면 다른 쪽도 자동 정리.
middleware (= proxy.ts)
건물 1층 보안 요원. 모든 요청이 페이지로 가기 전에 거쳐가는 코드. 출입증 없는 사용자를 로그인 페이지로 보냄.
PUBLIC_PATHS
출입증 없이도 들어갈 수 있는 라운지 목록. 여기 없는 페이지는 보안 요원이 막음.
Route Handler
화면이 아닌 처리 전용 엔드포인트. /auth/callback은 화면 없이 token 받아 처리한 후 다른 곳으로 보냄. "엘리베이터 안내원" 같은 역할.
verifyOtp / exchangeCodeForSession
Supabase가 제공하는 두 가지 신원 확인 방법. 메일 링크는 verifyOtp, 소셜 로그인(미래 도입)은 exchangeCodeForSession. 콜백 핸들러가 URL params 보고 둘 중 적절한 것 선택.
pg_cron
PostgreSQL 안에서 동작하는 알람 시계. 외부 서버 없이 DB가 정해진 시각에 자동으로 함수를 실행하게 해줌.
dry-run
"실제로 안 하고 미리 보기"만 하는 모드. cleanup 함수에 dry_run=true를 주면 삭제 안 하고 후보 수만 알려줌.
open redirect
URL 변조로 사용자를 우리 사이트 안에서 외부 악성 사이트로 튕기는 공격. ?next=//evil.com 같은 값. 우리 콜백은 /로 시작하는 상대 경로만 받음.
regression test (회귀 테스트)
새 코드가 기존 기능을 깨뜨렸는지 확인하는 자동 테스트. Phase 8은 430개가 모두 통과했어요.
